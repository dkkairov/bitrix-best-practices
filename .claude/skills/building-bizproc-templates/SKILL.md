# Бизнес-процесс Bitrix24 по ТЗ

## Суть
Процесс описывается спецификацией YAML, `.bpt` из неё собирает `tools/bpt/bpt.php`. Утилита покрыта
тестами на 14 реальных шаблонах. Твоя работа — спецификация и её соответствие ТЗ.
Источников хватает трёх: `bpt.php catalog`, `tools/bpt/SPEC.md`, образец
`tools/bpt/examples/invoice-approval.bizproc.yaml`.

## Результат
Папка `work/bizproc/<слаг>/` (в `.gitignore`: данные клиента):

| Файл | Что это |
|------|---------|
| `process.bizproc.yaml` | спецификация — единственный исходник, правки только в ней |
| `portal.yaml` | снимок портала, если делали свой |
| `process.bpt` | собранный шаблон |
| `schema.md` | схема для согласования с заказчиком |
| `README.md` | «Что делает», «Файлы», «Загрузка», «Тест», «Допущения», «Вопросы заказчику» |

## Порядок
1. **Снимок портала.** Есть экспорт любого шаблона того же документа —
   `php tools/bpt/bpt.php snapshot <экспорт>.bpt -o <папка>/portal.yaml` (поля и стадии), людей,
   группы, смарт-процессы впиши вручную. Есть только `tools/bpt/examples/example.portal.yaml` — он
   синтетический: файл годится лишь для теста, так и напиши в README.
2. **Готовый шаблон на входе** (изменить, разобрать): `decompile <экспорт>.bpt --portal=<снимок>
   -o process.bizproc.yaml`, дальше с шага 3; для ревью — `analyze` и `render`.
3. **Спецификация.** Действия — алиасы из `bpt.php catalog`, свойства — из `bpt.php catalog <алиас>`.
   ID портала — только `{{вид:Название}}`, результаты шагов — `{=@id:Результат}`. Кого нет в снимке
   (роль, руководитель) — константа шаблона `Type: user` и вопрос в README. «Сменить стадию» —
   последний шаг своей ветки: она завершает процесс, шаги после неё не выполняются (стенд, коробка);
   запись в историю и уведомления ставь до неё.
4. **Сборка:** `php tools/bpt/bpt.php compile <spec> --portal=<снимок> --strict --force -o process.bpt`.
   Ошибки чини в спецификации. Каждое предупреждение — убери или объясни в README.
5. **Схема:** `php tools/bpt/bpt.php render process.bpt -o schema.md`. Пройди её по ТЗ: у каждого
   требования есть шаг, у каждой ветки — осмысленный конец. Это и есть проверка результата: шаги 4–5
   без ошибок.
6. **README** — разделы из таблицы выше; ответы на таблицу ниже — в «Допущения» или «Вопросы».

## Решения, которые надо принять явно
| Вопрос | Что учесть |
|--------|-----------|
| Автозапуск | в `.bpt` его нет, задаётся при загрузке: «при создании» — `AUTO_EXECUTE=1`. «При изменении» (2, 3) запускает процесс на каждую правку пользователя, даже пока прежний ещё идёт: три правки — три параллельных согласования. Правки самого БП автозапуск не вызывают |
| Повторное согласование после доработки | без него документ не вернётся на согласование |
| Получатель — группа или отдел | `group_g<ID>` — группа пользователей, `group_d<ID>` / `group_dr<ID>` — отдел без / с подотделами, `group_hr…` / `group_hrr…` — узел оргструктуры. Какой нужен — из экспорта, где получатель уже выбран (`bpt.php analyze`), иначе вопрос |
| «История» в ТЗ | `crm_event` — запись в историю CRM, `timeline_comment` — комментарий в элементе; заказчики называют «историей» оба |
| Срок задания | `TimeoutDuration` пуст — задание ждёт без срока; нужен ли срок и что по истечении — вопрос |
| Кого ещё уведомить | ТЗ обычно называет одного получателя. Перебери остальных явно: инициатор, те, кто уже согласовал (их работа пропала — знают ли они), руководитель, ответственный. Кого ТЗ не назвало — вопрос |
| Исполнитель не может или отказывается | «Запрос информации» (`request_info`) отказа не имеет вовсе: не ответят — процесс ждёт вечно. Нужен отказ — `request_info_optional`, нужен предел ожидания — срок. Что делать при отказе и при молчании — вопрос |
| Значения свойств вне каталога | допустимые значения, где они известны, показывает `bpt.php catalog <алиас>`. Иначе впиши своё с комментарием `# проверить в дизайнере`, в «Тест» — пункт «после импорта открыть действие и сверить». Проверка в дизайнере надёжнее поиска в интернете |
| Способ загрузки | импорт в дизайнере, REST из приложения (`wiki/glossary/entity-bizproc-template-rest-methods.md`), в коробке ещё PHP — всё это один `CBPWorkflowTemplateLoader::ImportTemplate`, он проверяет свойства действий. Поля документа в файл не кладём (`--with-document-fields` создаёт их на портале). Роботы на стадиях в облаке — только вручную |

Ревью: до 10 шагов — сам по этой таблице; больше — можно отдать субагенту её же.

## Не делай
- `.bpt` и JSON руками — только спецификация и пересборка.
- Свои скрипты проверки утилиты (сверка «туда-обратно», контрольные суммы) — это её тесты.
- «Готово к загрузке» без оговорки: сначала тестовый портал. Импорт проверен на коробке, в облаке —
  нет; снимок с чужого или синтетического портала означает чужие ID.
- Действие «PHP-код» (`php_code`).

## Частые ошибки сборки
| Сообщение | Что делать |
|-----------|------------|
| `неизвестное действие «…»` | алиас из `bpt.php catalog` |
| `неизвестные свойства: …` | `bpt.php catalog <алиас>` — список свойств |
| `в снимке (…) нет …; есть: …` | дописать в снимок или спросить; «похожее» не подставлять |
| `встречается несколько раз … уточните` | полное название из списка в сообщении |
| `«сырые» идентификаторы портала` | заменить на `{{вид:Название}}` |
