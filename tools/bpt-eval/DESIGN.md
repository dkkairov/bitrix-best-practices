# Дизайн: оценка навыка «БП по ТЗ» на типовых задачах

**Статус:** согласован 2026-09-22 (обсуждение в Claude Code). Реализация — по плану.
**Область:** `tools/bpt-eval`. Это шаг 8 паттерна
[pattern-bizproc-ai-assisted-generation](../../wiki/modules/bizproc/pattern-bizproc-ai-assisted-generation.md):
«10–15 эталонных задач; метрики — проходит проверку → загружается → сценарий отрабатывает → ревьюер
согласен». Оцениваем навык
[building-bizproc-templates](../../.claude/skills/building-bizproc-templates/SKILL.md) вместе с
утилитой [tools/bpt](../bpt/README.md) на тестовом стенде
([рецепт стенда](../../wiki/development/server-admin/recipe-box-test-stand-docker.md)).

## 1. Задача и рамки

**Цель — решение по порогу.** Если **не меньше 80%** задач проходят все проверки без ручных
правок, навык можно давать команде на реальные ТЗ, а человек проверяет только схему процесса.
Кроме доли пройденных задач нужен список слабых мест навыка и утилиты — что чинить.

**Входит:** набор задач с проверками и эталонами, подготовка стенда, прогон агентов, прогонщик
сценариев на стенде, проверка чек-листа вопросов, отчёт, тесты.

**Не входит:** облако и загрузка через REST, процессы со статусами, роботы на стадиях, проверка
через интерфейс. Исправления навыка и утилиты по итогам — отдельными шагами после отчёта: сначала
видим провал, потом правим (TDD для навыков).

## 2. Решения, принятые при обсуждении (2026-09-22)

| Вопрос | Решение |
|--------|---------|
| Что на выходе | порог 80% задач + список слабых мест навыка и утилиты |
| Откуда ТЗ | смесь: 3–5 реальных ТЗ от команды (обезличенные, можно пересказом) + 10 задач, которые пишу я по конструкциям корпуса |
| Когда задача пройдена | сборка без ошибок, импорт прошёл, все сценарии на стенде отработали, все пункты чек-листа неоднозначностей подняты в README |
| Бюджет | 3 пилотные задачи (T01, T04, T10), затем остальные по одному прогону; упавшие после исправлений — повторно. Около 2,5 млн токенов |
| Подход | сценарии как данные (`acceptance.yaml`) + один прогонщик на PHP в контейнере стенда. Агент получает готовый снимок портала и к стенду не ходит |
| Роли | как в практике команды: **группы пользователей** и **поля-роли в карточке «Проекта»**, к которому привязана заявка («Руководитель проекта», «Сметчик», «Бухгалтер проекта»). Отделы и константы — в одной-двух задачах |
| Эталоны (уточнение при записи спецификации) | к каждой задаче — эталонное решение: оно обязано пройти свои сценарии до запуска агентов. Так ошибка проверки не выдаётся за ошибку агента |

## 3. Архитектура

```
tools/bpt-eval/
  eval.php                 CLI на хосте: prepare, reference, check, report
  src/
    Acceptance.php         чтение и проверка формата acceptance.yaml
    Roles.php              роли из roles.yaml: название → вид (группа, поле проекта, сотрудник, отдел)
    ConstantMatcher.php    сопоставление констант-пользователей шаблона с ролями
    Report.php             сводка результатов в report.md
  stand/                   скрипты, которые выполняются в контейнере php стенда
    setup.php              подготовка стенда (идемпотентно)
    snapshot.php           снимок портала для агентов
    import.php             импорт шаблона (ImportTemplate) с нужным автозапуском
    runner.php             сценарии: элементы, задания, проверки
    cleanup.php            уборка после задачи
  tasks/Txx-<слаг>/
    tz.md                  ТЗ так, как его видит агент
    acceptance.yaml        сценарии и чек-лист
    reference.bizproc.yaml эталонное решение (у T10 нет)
  roles.yaml               роли → группы, поля «Проекта», сотрудники (по именам, без ID стенда)
  AGENT_PROMPT.md          задание агенту
  CHECKLIST_PROMPT.md      задание проверяющему чек-лист
  tests/run.php            тесты без стенда
  DESIGN.md, README.md

work/eval/<прогон>/        вне git: portal.yaml, папки задач агентов, result.json, report.md
```

Поток данных:

```
prepare   → стенд: группы, «Проекты», привязка, «Проект Альфа», поля и стадии «Заявок» → portal.yaml
reference → эталоны задач через check → должны пройти 100% сценариев
агенты    → work/eval/<прогон>/Txx/: process.bizproc.yaml, process.bpt, schema.md, README.md
check     → пересборка с --strict → импорт → константы → сценарии → уборка → result.json
чек-лист  → дешёвый агент читает README → checklist.json
report    → report.md: таблица, доля пройденных против порога, слабые места
```

`eval.php` работает на хосте, как `bpt.php`. Со стендом говорит через
`docker compose exec -T --user=bitrix php php` (как скрипты пилота): входные данные — JSON в
переменной окружения, результат — JSON в stdout. Папка стенда — из `BPT_EVAL_STAND`
(по умолчанию `C:/docker/b24-test`). Сборку и разбор выполняет существующий `tools/bpt`.

## 4. Задачи

Каждая задача — просьба менеджера проекта: коротко, с недомолвками, как в жизни. Недомолвки
заложены намеренно — это чек-лист (раздел 5). Документ во всех задачах — «Заявки», привязанные к
«Проекту».

| # | Задача | Конструкции | Откуда роли | Заложенные неоднозначности |
|---|--------|-------------|-------------|----------------------------|
| T01 | Согласование суммы бухгалтерией (как в пилоте) | утверждение, история, уведомление, стадии | группа «Бухгалтеры» или отдел «Бухгалтерия» — в обоих есть бухгалтер | группа или отдел, «история», повторное согласование, срок |
| T02 | До 100 тыс. — руководитель проекта, выше — финдиректор | условие, два утверждения | поле проекта + группа | граница включительно, пустая сумма |
| T03 | Последовательно: юрист → руководитель проекта → гендиректор; отказ на любом шаге — «Доработка» и причина инициатору | вложенные утверждения | группа + поле проекта + сотрудник | кому причина, что с уже согласившими |
| T04 | Параллельно юрист и бухгалтер проекта; «Согласовано» только если оба «да» | параллельные ветки, переменные | группа + поле проекта | ждать ли второго после первого «нет» |
| T05 | После отказа инициатор описывает исправления, снова на согласование; после трёх отказов — «Провал» | цикл, счётчик, запрос информации | поле проекта | кто дорабатывает, как считать попытки |
| T06 | Ознакомить юридический отдел с новой заявкой, в историю — кто ознакомился | ознакомление | отдел | все или любой, срок |
| T07 | Бухгалтер проекта вносит номер счёта и дату оплаты, они пишутся в поля, стадия «Оплачено» | запрос информации, изменение полей | поле проекта | обязательность полей, что при отказе |
| T08 | Задача сметчику проекта «Подготовить смету», срок +3 рабочих дня | задача, формула срока | поле проекта | постановщик, ждать ли выполнения |
| T09 | После утверждения — поле «Согласовано кем», руководитель проекта в наблюдатели | изменение полей, наблюдатели | поле проекта | формат поля, какой руководитель |
| T10 | Уведомить клиента письмом на e-mail | **действия нет в каталоге** | — | агент должен сказать, что это недоступно, и предложить замену |
| R1–R5 | реальные ТЗ команды | — | — | по содержанию |

**Пилотная тройка:** T01 (контроль — повторяет пилот), T04 (параллель и поля проекта), T10
(нет действия). Реальные ТЗ можно прислать после пилота; основной прогон их ждёт.

Задачи в git только обезличенные. Реальное ТЗ, которое не удалось обезличить, живёт в
`work/eval/` и в git не попадает.

## 5. Формат проверок (`acceptance.yaml`)

**Принцип:** сценарий проверяет только то, что ТЗ говорит **однозначно**. Всё неоднозначное — в
чек-лист, чтобы разумный выбор агента не штрафовался. Проверяется наблюдаемое поведение (кто
получил задание, что стало после ответа), а не устройство процесса.

```yaml
task: T04
document: Заявки
start: create                    # как стартует процесс по ТЗ: create | manual
parameters: {}                   # значения параметров при start: manual
item:                            # элемент, на котором гоняем сценарии (поля — по названиям)
  Название: Заявка T04
  Сумма к оплате: 250000
  Проект: Проект Альфа
scenarios:
  - name: оба согласовали
    steps:                       # задания в любом порядке, если параллельные
      - task_for: Юристы         # роль из roles.yaml
        do: approve              # approve | reject | review | provide | complete
        comment: Юридически чисто
      - task_for: Бухгалтер проекта
        do: approve
    expect:
      stage: Согласовано
      process: completed         # completed | running
  - name: юрист отказал
    steps:
      - task_for: Юристы
        do: reject
        comment: Нет доверенности
    expect:
      stage: Доработка
checklist:                       # что агент должен поднять в README
  - Ждать ли второго согласующего после первого отказа
  - Повторное согласование после доработки
```

**Шаги:** `task_for` — роль, чьё задание ищем (любого пользователя этой роли); `do` — действие;
`comment` — комментарий к решению; для `provide` — `values: {поле: значение}`; необязательно
`title_contains` — фрагмент названия задания.

**Проверки `expect`:** `stage`; `fields: {поле: значение}`; `history_contains: [фрагмент]`;
`notify: [{to: роль, contains: фрагмент}]`; `task_created: [{responsible: роль, title_contains,
deadline_workdays}]`; `observers: [роль]`; `process`; `no_task_for: [роль]`.

**Чек-лист:** пункты — строки; пункт с `required: false` в итог «пройдена» не входит, только в
оценку качества вопросов.

## 6. Роли и стенд

`roles.yaml` — названия, без ID стенда:

```yaml
Юристы:            {group: Юристы}
Финансовый отдел:  {group: Финансовый отдел}
Бухгалтерия:       {group: Бухгалтеры}          # группа; одноимённый отдел «Бухгалтерия» тоже есть
Юридический отдел: {department: Юридический отдел}
Руководитель проекта: {project_field: Руководитель проекта}
Бухгалтер проекта:    {project_field: Бухгалтер проекта}
Сметчик:              {project_field: Сметчик}
Генеральный директор: {user: Генеральный директор Тест}
Инициатор:            {user: Инженер ПТО Тест}
```

**`prepare` создаёт** (повторный запуск ничего не дублирует):
- группы пользователей «Юристы», «Финансовый отдел», «Бухгалтеры» и их состав. Имена групп не
  совпадают с названиями отделов, иначе снимок сочтёт название неоднозначным;
- смарт-процесс «Проекты» с полями-сотрудниками «Руководитель проекта», «Сметчик», «Бухгалтер
  проекта» и привязку «Заявок» к «Проектам»;
- «Проект Альфа» с заполненными ролями;
- в «Заявках» — недостающие поля («Номер счёта», «Дата оплаты», «Согласовано кем») и стадии
  («Согласовано», «Оплачено», «Провал»);
- снимок портала для агентов `work/eval/<прогон>/portal.yaml`: поля и стадии «Заявок», сотрудники,
  группы, отделы, смарт-процессы — автоматически, а не вручную, как в пилоте.

Пользователей `prepare` не создаёт: это делает человек.

## 7. Прогонщик (`check`)

Для одной задачи, строго по одной на стенде:
1. **Сборка.** Пересборка спецификации агента `bpt.php compile --portal=<снимок> --strict`. Ошибка —
   провал «сборка».
2. **Импорт** через `CBPWorkflowTemplateLoader::ImportTemplate` (тот же путь, что дизайнер и REST)
   с автозапуском из `start`; имя шаблона `EVAL <прогон> <задача>`. Отказ импорта — провал «импорт».
3. **Константы.** Если у шаблона есть константы-пользователи, `ConstantMatcher` сопоставляет их
   название с ролями (`Руководитель проекта` → поле проекта). Не сопоставилось — провал с этой
   причиной.
4. **Сценарии.** Для каждого: создать элемент (или запустить процесс вручную) → по шагам найти
   открытое задание нужной роли (ждём до 10 секунд) → ответить от имени этого пользователя →
   проверить `expect`. Результат по каждой проверке — в `result.json`.
5. **Уборка:** деактивировать шаблон, остановить незавершённые процессы на элементах задачи.
   Элементы остаются для разбора (в названии — `EVAL`). Перед задачей прогонщик убеждается, что на
   «Заявках» нет другого активного шаблона `EVAL` с автозапуском.

**Категории провала:** `spec` — ошибка в спецификации агента; `tool` — недостаток утилиты; `skill` —
пробел в навыке (агент сделал то, что навык разрешает, а результат неверный); `harness` — сбой
прогонщика или стенда. `harness` против навыка не засчитывается: чиним и перегоняем.

`reference` — тот же `check`, но на эталонном решении задачи; до агентов все эталоны должны пройти.

## 8. Агенты

- **Исполнитель:** отдельный субагент на задачу, задание — `AGENT_PROMPT.md`: прочитать навык,
  ТЗ, снимок `work/eval/<прогон>/portal.yaml`; писать только в папку задачи; стенд, Docker и
  репозиторий не трогать; уточнить у заказчика нельзя. По 3 параллельно в фоне. Расход (токены,
  вызовы, время) я записываю в `work/eval/<прогон>/agents.json` по уведомлениям о завершении.
- **Проверяющий чек-лист:** дешёвая модель, задание — `CHECKLIST_PROMPT.md`: README задачи + пункты
  чек-листа → JSON `{пункт, поднят: да/нет, цитата}`. Без цитаты «поднят» не засчитывается. Спорные
  ответы я проверяю выборочно.

## 9. Отчёт

`work/eval/<прогон>/report.md`: таблица по задачам — сборка, импорт, сценарии x/y, чек-лист x/y,
итог, токены, время, категория провала. Под таблицей — доля пройденных задач против порога 80% и
вывод; слабые места по категориям и что правим. После исправлений упавшие задачи перегоняются,
отчёт дополняется таблицей «до/после». Кратко итог — в паттерн (шаг 8) и в `log.md`.

По одному прогону на задачу порог оценивается грубо — отчёт это прямо говорит.

## 10. Тесты

Без стенда, `php tools/bpt-eval/tests/run.php`: разбор и проверка `acceptance.yaml` (ошибки
формата с путём), разрешение ролей по видам, сопоставление констант, сводка отчёта (доля, порог,
категории). Скрипты стенда проверяются эталонами: `reference` на всех задачах — это их интеграционный
тест.

## 11. Риски

| Риск | Как обходим |
|------|-------------|
| Снимок описывает поля только документа процесса, а роли берутся из полей «Проекта»: агенту и эталону придётся писать сырые коды, `--strict` это запрещает | Проявится на эталонах T02–T05, T07–T09 до запуска агентов. Тогда до агентов расширяем снимок и утилиту полями связанных смарт-процессов — отдельный блок с тестами |
| Реальных ТЗ пока нет | Пилот идёт без них; основной прогон — после того, как команда пришлёт 3–5 |
| Разброс агента при одном прогоне | Отчёт прямо говорит о грубости оценки; упавшие задачи после исправлений перегоняются |
| Задачи мешают друг другу через автозапуск | Уборка после каждой задачи и проверка перед ней (раздел 7) |
| Эвристика констант ошибётся | Причина пишется в результат; такой провал разбираю вручную, при ошибке эвристики — `harness` |
| Проверяющий чек-лист субъективен | Нужна цитата из README; выборочная ручная проверка |
| Стенд «плывёт» от прогона к прогону | `prepare` идемпотентен; элементы и шаблоны задач помечены `EVAL` |

## 12. Критерии готовности

1. `prepare`, `reference`, `check`, `report` работают; тесты без стенда проходят.
2. Эталон каждой задачи (кроме T10) проходит все свои сценарии.
3. Пилотная тройка прогнана агентами, отчёт по ней, выводы по прогонщику учтены.
4. Основной прогон всех задач (с реальными ТЗ), отчёт, решение по порогу, список слабых мест.
5. Итог — в паттерне (шаг 8) и `log.md`; всё закоммичено по блокам.
