# tools/bpt-eval — оценка навыка «БП по ТЗ»

Прогоняет навык Claude Code
[`building-bizproc-templates`](../../.claude/skills/building-bizproc-templates/SKILL.md) вместе с
утилитой [`tools/bpt`](../bpt/README.md) на типовых ТЗ: агент по каждому ТЗ собирает бизнес-процесс,
прогонщик проверяет результат сценариями на тестовом стенде. Итог — решение «навык можно давать
команде на реальные ТЗ» по порогу **80%** пройденных задач и список слабых мест навыка и утилиты.
Полный дизайн и обоснование решений — [DESIGN.md](DESIGN.md); план реализации по шагам —
[PLAN.md](PLAN.md). Стенд — [рецепт установки](../../wiki/development/server-admin/recipe-box-test-stand-docker.md).

## Требования

- PHP ≥ 8.1 на хосте с расширением `yaml` (`tz.md`/`acceptance.yaml`/`roles.yaml`/`portal.yaml` —
  YAML; сборку спецификаций делает `tools/bpt`, требования те же).
- Для `prepare`, `reference` и `check` — запущенный тестовый стенд коробки Битрикс24 в Docker
  (`docker compose up` в папке стенда). Путь к папке — переменная окружения `BPT_EVAL_STAND`,
  по умолчанию `C:/docker/b24-test`. `usage` и `report` стенд не трогают — только читают и пишут
  файлы прогона на хосте.
- Запуск — из корня репозитория.

## Команды

| Команда | Нужен стенд | Что делает |
|---------|:-----------:|-----------|
| `prepare --run=<прогон>` | да | готовит стенд (группы, смарт-процесс «Проекты», «Проект Альфа», недостающие поля/стадии «Заявок» — идемпотентно) и пишет снимок портала `work/eval/<прогон>/portal.yaml` |
| `reference <задача\|all> --run=<прогон>` | да | тот же путь проверки, что `check`, но на эталонном решении задачи (`tasks/Txx-.../reference.bizproc.yaml`); результат — `work/eval/_reference/<прогон>/<задача>/`, вне папки прогона |
| `check <задача> --run=<прогон>` | да | проверяет решение агента: сборка `--strict` → импорт в стенд → сопоставление констант-пользователей с ролями → сценарии `acceptance.yaml` → уборка; пишет `result.json` |
| `usage <задача> --run=<прогон> --tokens=N --tools=N --ms=N` | нет | записывает расход агента (токены, вызовы инструментов, время) в `work/eval/<прогон>/agents.json` |
| `report --run=<прогон>` | нет | собирает `result.json` + `checklist.json` + `agents.json` всех задач прогона в `work/eval/<прогон>/report.md` (и печатает в stdout): таблица по задачам, доля пройденных против порога, слабые места по категориям |

`--run=<прогон>` — обязателен для всех команд (буквы, цифры, «-», «_», «.»); отделяет прогоны друг от
друга в `work/eval/`.

## Порядок полного прогона

Так это реально устроено — от подготовки стенда до готового отчёта:

1. **`php tools/bpt-eval/eval.php prepare --run=<прогон>`** — стенд готов, снимок портала записан.
   Для задач `review`/`modify` сразу за ним — `input <задача> --run=<прогон>`.
2. **`php tools/bpt-eval/eval.php reference all --run=<прогон>`** — эталоны всех задач должны пройти
   («эталон прошёл» по каждой). Не прошёл эталон — чинить прогонщик или формат задачи, а не подгонять
   эталон: иначе ошибка проверки будет по ошибке засчитана агенту. Результат ложится в
   `work/eval/_reference/<прогон>/<задача>/` — вне папки прогона, где на следующем шаге пишут агенты.
3. **Агенты по [`AGENT_PROMPT.md`](AGENT_PROMPT.md)** — подставить `{{REPO}}` (путь к репозиторию, тот
   же, что у оркестратора — так задание работает у любого в команде, а не только по пути автора),
   `{{TASK}}` (код задачи), `{{TZ}}` (текст из `tasks/Txx-.../tz.md`), `{{RUN}}` (прогон); запускать по
   три параллельно в фоне. Оркестратор, который создаёт агентов и подставляет плейсхолдеры, — **сессия
   Claude Code, а не сам агент**. Каждый агент пишет решение в `work/eval/<прогон>/<задача>/`:
   `process.bizproc.yaml`, `process.bpt`, `schema.md`, `README.md` — и ничего вне этой папки.
   Перезапуск задачи начисто: если решение агента перегоняется (испортилось, задание изменилось и т.п.),
   папку `work/eval/<прогон>/<задача>/` перед повторным запуском удалить целиком и в новом задании не
   упоминать, что там что-то уже было, — иначе агент прочитает следы прежней попытки и это тоже испортит
   задачу.
4. **`php tools/bpt-eval/eval.php check <задача> --run=<прогон>`** — по каждой задаче агентов
   отдельно (строго по одной на стенде, не параллельно).
5. **Чек-лист по [`CHECKLIST_PROMPT.md`](CHECKLIST_PROMPT.md)** — подставить `{{README_PATH}}`
   (README решения агента), `{{ITEMS}}` (пункты `checklist` из `acceptance.yaml` задачи), `{{OUT}}`
   (`work/eval/<прогон>/<задача>/checklist.json`). Проверяющий — дешёвая модель; спорные ответы стоит
   выборочно перепроверить самому.
6. **`php tools/bpt-eval/eval.php usage <задача> --run=<прогон> --tokens=… --tools=… --ms=…`** — по
   каждой задаче, когда известен расход агента (шаг 3).
7. **Разбор провалов вручную** — в `result.json` непройденной задачи проставить `category`
   (`spec` — ошибка в решении агента, `tool` — недостаток утилиты `tools/bpt`, `skill` — пробел в
   навыке, `harness` — сбой прогонщика или стенда) и `note` с кратким пояснением. `harness` не
   засчитывается против навыка: чиним прогонщик/стенд и перегоняем `check` для этой задачи без
   повторного вызова агента.
8. **`php tools/bpt-eval/eval.php report --run=<прогон>`** — итоговый `work/eval/<прогон>/report.md`:
   таблица по задачам, доля пройденных против порога 80%, слабые места по категориям провала.

## Виды задач

Поле `kind` в `acceptance.yaml`:

| `kind` | Что делает агент | Чем оценивается |
|--------|------------------|-----------------|
| `build` (по умолчанию) | собирает процесс по ТЗ | сборка → импорт → сценарии на стенде + чек-лист вопросов в README |
| `modify` | правит готовый шаблон (`input.bpt`) | то же плюс `preserved`: заголовки действий, которые обязаны уцелеть — иначе агент собрал похожий процесс заново вместо правки |
| `review` | разбирает чужой шаблон и пишет `review.md` | эталонные списки `defects` (обязан найти) и `traps` (ложная тревога) |

Задачам `review` и `modify` нужен входной шаблон: `input.bizproc.yaml` в папке задачи, из него
команда `input` собирает `work/eval/<прогон>/<задача>/input.bpt`. **Агент получает только `.bpt`** —
спецификация входа была бы ответом на задачу.

**Про ловушки.** Ловушка — техническое утверждение, ложное по факту: «утверждать, что смену стадии
надо поставить не последней, — ошибка». Вопрос заказчику («кто именно согласует», «нужна ли стадия
на время согласования») ловушкой быть не может — этого от агента и ждут, он же требуется таблицей
решений навыка. Первая версия R02 на этом и ошиблась: прогон `mode-1` показал, что так наказывают
за правильное поведение.

## Задачи и результаты прогона

```
tasks/Txx-<слаг>/
  tz.md                  ТЗ так, как его видит агент (недомолвки — намеренно, это чек-лист)
  acceptance.yaml         сценарии проверки и чек-лист неоднозначностей (формат — DESIGN.md §5)
  reference.bizproc.yaml  эталонное решение (нет только у задач без сценариев, напр. T10)
roles.yaml                названия ролей задач → кто это на стенде (группа/отдел/поле «Проекта»/сотрудник)
```

`T11-ruchnoy-zapusk` — служебная задача прогонщика, а не тестовый кейс навыка: проверяет ветки формата
`start: manual` и `parameters` (DESIGN.md §5), которые ни одна содержательная задача не задействует.
У неё нет осмысленного ТЗ, и агентам она не выдаётся (`tz.md` — одна строка об этом); `reference all`
проверяет её наравне с остальными.

Роли в `roles.yaml` — только имена; ID стенда прогонщик находит сам. Группы и смарт-процесс
«Проекты» создаёт `prepare`; сотрудников на стенде заводит человек.

**Результаты прогона — `work/eval/<прогон>/`, вне git** (весь `work/` в `.gitignore`): снимок
портала, папки задач с решениями агентов (`work/eval/<прогон>/<задача>/`, пишет сам агент, там же —
`result.json`/`checklist.json`), `agents.json`, `report.md`.

**Эталоны лежат отдельно — `work/eval/_reference/<прогон>/<задача>/`** (тоже вне git): туда `eval.php
reference` кладёт сборку, импорт и результат сценариев эталонного решения задачи. Папка нарочно вне
`work/eval/<прогон>/`, где пишет агент-исполнитель, — чтобы готовое решение не оказалось у него перед
глазами рядом с собственной рабочей папкой. `Report::fromRunDir` собирает задачи прогона строго с
глубиной в один уровень (`work/eval/<прогон>/*/result.json`), поэтому эталоны в отчёт прогона не
попадают, даже если запустить `report` до и после `reference`.

В репозиторий идут только обезличенные задачи (`tasks/`); реальное ТЗ, которое не удалось обезличить,
остаётся в `work/eval/` и в git не попадает.

## Ограничения оценки

- **Один прогон на задачу** — доля пройденных и порог 80% оцениваются грубо; `report.md` прямо это
  указывает. Упавшие после исправлений задачи перегоняются повторно.
- **Не входят:** облако и загрузка через REST, процессы со статусами, роботы на стадиях, проверка
  через интерфейс портала (см. DESIGN.md §1). Навык и утилита проверяются на коробке, сценарии
  выполняются через API ядра, а не кликами в дизайнере.
- **`check` меняет стенд**: импортирует шаблон (`EVAL <прогон> <задача>`) с автозапуском по
  `acceptance.yaml`, по сценариям создаёт элементы (`EVAL <задача>: <сценарий>`) и отвечает на
  задания от имени пользователей ролей. После задачи шаблон деактивируется и незавершённые процессы
  останавливаются, но сами элементы остаются на стенде для разбора. Без запущенного Docker-стенда
  (`BPT_EVAL_STAND`) `prepare`/`reference`/`check` не работают.

## Тесты

```bash
php tools/bpt-eval/tests/run.php                    # без стенда: формат acceptance.yaml, роли,
                                                      # сопоставление констант, сводка отчёта
php tools/bpt-eval/tests/run.php --filter=Отчёт      # часть тестов
```

Скрипты стенда (`stand/`) отдельных тестов не имеют — их проверяет `reference all` на всех задачах
как интеграционный тест.
