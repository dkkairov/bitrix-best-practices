# Дизайн: каталог действий и сборщик спецификаций БП

**Статус:** согласован 2026-09-18 (обсуждение в Claude Code). Реализация — следующим шагом.
**Область:** `tools/bpt`. Формат `.bpt` описан в вики:
[concept-bizproc-bpt-format](../../wiki/modules/bizproc/concept-bizproc-bpt-format.md).

## 1. Задача и рамки

Агент (Claude Code) пишет **спецификацию** процесса, детерминированный код собирает из неё `.bpt`,
человек проверяет **схему**, тестовый портал подтверждает поведение. Этот дизайн закрывает шаги 2–3
паттерна [pattern-bizproc-ai-assisted-generation](../../wiki/modules/bizproc/pattern-bizproc-ai-assisted-generation.md):
каталог действий и сборщик.

**Входит в блок:** каталог действий, `compile` (спецификация → `.bpt`), `decompile` (`.bpt` →
спецификация), `render` (схема Mermaid), `snapshot` (снимок портала из `.bpt`), тесты, документация.

**Не входит:** REST (живой снимок портала, загрузка шаблона, прогон процессов), навык Claude Code,
хуки, процессы со статусами (`StateMachineWorkflowActivity`).

**Решение по языку спецификаций** (2026-09-18): спецификации пишет агент, люди проверяют схему,
поэтому язык повторяет Bitrix **один в один** — реальные имена свойств из каталога, без
промежуточного «человеческого» слоя. Упрощённые команды поверх, если понадобятся, добавим после
пилота.

## 2. Архитектура

```
tools/bpt/
  bpt.php                  CLI: decode, encode, check, analyze, compact (есть)
                           + catalog, compile, decompile, render, snapshot (новые)
  src/
    BptFile.php            чтение и запись .bpt, JSON, кодировки
    Analyzer.php           текущие проверки (перенос из bpt.php)
    Catalog.php            каталог: типы, алиасы, свойства, формы вложенности, нормализация
    SpecReader.php         чтение спецификации: YAML (ext-yaml) или JSON
    Compiler.php           спецификация → дерево действий → .bpt
    Decompiler.php         .bpt → спецификация
    Snapshot.php           снимок портала: загрузка, извлечение из .bpt, поиск ID по названию
    Mermaid.php            схема процесса
  catalog/activities.php   каталог 23 типов действий
  examples/                синтетические спецификация и снимок
  tests/run.php            тесты
  SPEC.md                  формат спецификации (для людей и агента)
  DESIGN.md                этот документ
  README.md                команды и ограничения
```

Поток данных:

```
спецификация + снимок + каталог ─ compile ─→ дерево ─→ проверки ─→ .bpt
.bpt (+ снимок) ─ decompile ─→ спецификация          (библиотека примеров, сверка «туда-обратно»)
.bpt | спецификация ─ render ─→ схема Mermaid        (ревью человеком)
.bpt ─ snapshot ─→ снимок портала                    (поля и стадии из DOCUMENT_FIELDS)
```

Каждый класс решает одну задачу и тестируется отдельно; `bpt.php` остаётся тонким — разбор
аргументов и вызов класса.

Новые команды:

```
bpt.php catalog [Тип] [--json]                       каталог действий: таблица или JSON
bpt.php compile <spec.yaml> -o <out.bpt> [--portal <снимок>] [--strict] [--force]
bpt.php decompile <file.bpt> [-o <spec.yaml>] [--portal <снимок>] [--keep-names] [--json]
bpt.php render <file.bpt|spec.yaml> [-o <схема.md>] [--portal <снимок>]
bpt.php snapshot <file.bpt> [-o <снимок.portal.yaml>] [--json]
```

Вывод по умолчанию — в stdout, как у существующих команд; `-o` пишет в файл.

## 3. Формат спецификации v1

YAML (по умолчанию) или JSON — структура одна и та же.

```yaml
bizproc: 1                        # версия формата
name: Согласование выплаты        # имя процесса; в .bpt не пишется (задаётся при загрузке)
# kind убран 2026-09-21: по .bpt роботов от дизайнера не отличить (см. раздел 11)
document: "DYNAMIC_{{smart:Заявки}}"   # тип документа: сверка со снимком, подсказка при загрузке
parameters: {}                    # как в .bpt: код → {Name, Type, Required, Multiple, Default, …}
variables:
  amount: {Name: Сумма к оплате, Type: double, Required: true}
constants: {}
steps:
  - request_info_optional:
      id: approve
      title: Согласование бухгалтером
      Users: ["{{group:Бухгалтерия}}"]
      RequestedInformation: [{Name: amount, Title: Сумма, Type: double, Required: true}]
      on_yes:
        - crm_event:
            EventType: INFO
            EventText: "Сумма: {=Variable:amount > printable}"
            EventUser: ["{=@approve:InfoUser}"]
        - change_stage: {TargetStatus: "{{stage:Клиент}}"}
      on_no:
        - change_stage: {TargetStatus: "{{stage:Доработка}}"}
```

### Шаг
Ключ шага — алиас действия из каталога (`request_info_optional`) или его тип
(`RequestInformationOptionalActivity`). Значение — служебные ключи вместе со свойствами Bitrix.

| Служебный ключ | Смысл |
|----------------|-------|
| `id` | логическое имя шага для ссылок `{=@id:Результат}` |
| `title` | заголовок действия (`Properties.Title`); без него берётся заголовок по умолчанию из каталога |
| `off: true` | действие отключено (`Activated: "N"`) |
| `comment` | `Properties.EditorComment` |
| `name` | реальное имя действия (`A…`); только для точной сверки «туда-обратно» |
| `raw` | свойства вне каталога — передаются как есть, с предупреждением |
| `on_yes`, `on_no` | ветки действий с двумя исходами (утверждение, запрос информации) |

Остальные ключи — свойства Bitrix с их реальными именами (`Users`, `Fields`, `TargetStatus`).
Не указанные свойства заполняются значениями по умолчанию из каталога.

### Структурные шаги

```yaml
- if:
    title: Сумма заполнена?
    branches:
      - {title: Да, when: {fieldcondition: [["{{field:Сумма}}", "!empty", "", "0"]]}, steps: [...]}
      - {title: Иначе, else: true, steps: [...]}
- parallel: {branches: [[...шаги...], [...шаги...]]}
- while: {when: {fieldcondition: [...]}, steps: [...]}
- block: {title: Согласование, steps: [...]}
```

Ветка `parallel` — список шагов или объект `{title, id, off, steps}`. Ветка `if` без `when` и без
`else` компилируется в ветку без условия — так бывает в реальных шаблонах.

### Условия
Записываются как в Bitrix: `fieldcondition` и `propertyvariablecondition` — списки
`[имя, оператор, значение, связка]`, `mixedcondition` — объекты
`{object, field, operator, value, joiner}`, `else: true` → `truecondition: "1"`.
Связка `"0"` / `"1"` по наблюдениям означает «и» / «или» (эмпирика, см. §11).

### Выражения и подстановки
- Выражения Bitrix пишутся как есть: `{=Document:TITLE > friendly}`, `{=Variable:x}`,
  `{=System:Now}`, формулы `=workdateadd(...)`.
- Ссылка на результат шага — `{=@id:Результат}`; сборщик заменяет её на `{=A…:Результат}`.
- Плейсхолдеры портала — `{{field|stage|user|group|smart|template:Название}}`. Работают в любом
  месте строки и в ключах отображений (например, в `FieldValue`).

### Нормализация значений
YAML 1.1 превращает `Y`, `N`, `yes`, `on` в булевы значения, а Bitrix хранит строки. Поэтому
сборщик приводит значения к виду Bitrix:

| Что | Во что |
|-----|--------|
| `true` / `false` в свойствах | `"Y"` / `"N"` |
| `true` / `false` в `Required`, `Multiple` описаний полей | `"1"` / `"0"` |
| числа | строки (`50` → `"50"`) |
| `null` | остаётся `null` там, где каталог это допускает |

### Имена действий
`Name` вида `A…` генерируется детерминированно из имени процесса и пути шага, поэтому повторная
сборка одной и той же спецификации даёт тот же файл. Коллизии проверяются; при совпадении имя
пересчитывается с солью. Если в шаге указан `name`, берётся он.

## 4. Каталог действий

`catalog/activities.php` — PHP-массив (комментарии рядом с записями). Запись на тип:

```php
'ApproveActivity' => [
    'alias'    => 'approve',
    'title'    => 'Утверждение документа',      // заголовок по умолчанию
    'shape'    => 'waiting-branches',
    'props'    => [
        'Users'           => ['type' => 'list', 'required' => true],
        'ApproveType'     => ['type' => 'str',  'default' => 'all'],
        'TimeoutDuration' => ['type' => 'str',  'default' => ''],
        // …остальные свойства с типами и значениями по умолчанию
    ],
    'returns'  => ['Comments', 'LastApprover'],  // встречались в ссылках корпуса
    'observed' => 4,                             // сколько раз встретилось в корпусе
],
```

Формы вложенности:

| `shape` | Дети | Примеры |
|---------|------|---------|
| `leaf` | нет | изменение поля, смена стадии, уведомление |
| `waiting` | нет, но ждёт людей | ознакомление, запрос информации |
| `waiting-branches` | ровно две последовательности: `on_yes`, `on_no` | утверждение, запрос информации с отказом |
| `ifelse` | ветки `IfElseBranchActivity` | условие |
| `parallel` | последовательности, минимум две | параллельное выполнение |
| `loop` | условие и одна последовательность | цикл |
| `block` | одна последовательность | блок действий |

Служебные типы (`SequentialWorkflowActivity`, `SequenceActivity`, `IfElseBranchActivity`) в
спецификации не пишутся — их создаёт сборщик.

Типы свойств: `str`, `text`, `expr`, `yn`, `list`, `map`, `portal-id`. Тип задаёт нормализацию и
проверки; `portal-id` дополнительно помечает привязку к порталу (`TemplateId`, `DynamicTypeId`).

Команда `bpt.php catalog` печатает каталог таблицей (для вики) или в JSON (для агента);
`bpt.php catalog Task2Activity` — одну запись.

## 5. Снимок портала

Файл `*.portal.yaml` / `*.portal.json`. Содержит данные клиента, поэтому **в git не попадает**:
в `.gitignore` добавляются `*.portal.yaml` и `*.portal.json`, а синтетический пример в
`tools/bpt/examples/` вносится явным исключением.

```yaml
document: DYNAMIC_1000
fields:    {"Сумма к оплате": UF_CRM_7_1700000000001}
stages:    {"Общая/Клиент": "DT1000_10:CLIENT"}
users:     {"Иванов Иван": user_42}
groups:    {"Бухгалтерия": group_g7}
smart:     {"Заявки": 1000}
templates: {"Обязательное согласование": 900}
document_fields: {…}     # полная копия DOCUMENT_FIELDS, если снимок сделан из .bpt
```

- Снимок хранит **готовое значение** (`group_g7`), поэтому сборщику не нужно знать формат токенов
  пользователей, групп и отделов.
- `bpt.php snapshot file.bpt` заполняет `fields`, `stages` и `document_fields` из `DOCUMENT_FIELDS`.
  При совпадении названий к ним добавляется код: `«Ответственный [ASSIGNED_BY_ID]»`. Остальные
  разделы заполняются вручную, позже — REST-скриптом.
- Поиск по названию: без учёта регистра и внешних пробелов. Для стадии подходит и
  `«Воронка/Стадия»`, и просто `«Стадия»`, если название однозначно.
- Нет совпадения или их несколько — ошибка со списком кандидатов.
- `DOCUMENT_FIELDS` в собранном файле по умолчанию пуст; из снимка — только с
  `--with-document-fields`. **Изменено 2026-09-22** по итогам стенда: импорт создаёт на портале
  поля из `DOCUMENT_FIELDS`, которых там нет, а пустой раздел пропускает (см. §11).

## 6. Сборка и проверки

Этапы `compile`: чтение спецификации → нормализация значений → построение дерева по каталогу →
подстановка плейсхолдеров и ссылок → проверки → запись `.bpt`.

**Ошибки** (файл не пишется):
- неизвестный тип или алиас действия; неизвестное свойство (каталог закрытый, обход — через `raw`);
- нет обязательного свойства;
- нарушена форма вложенности: `on_yes` у простого действия, `if` с одной веткой, `while` без условия,
  `steps` у листа, `when` вместе с `else`;
- повтор `id`; ссылка `{=@id:…}` на несуществующий шаг;
- плейсхолдер не найден в снимке или найден неоднозначно;
- ошибки `analyze` на собранном дереве: висячие ссылки `{=A…}`, необъявленные переменные, константы
  и параметры, запрещённые действия.

**Предупреждения:** результат вне списка `returns`; свойства через `raw`; «сырые» ID портала в
спецификации (с `--strict` — ошибка); ожидания без таймаута; циклы; поля, которых нет в
`document_fields` снимка.

Ошибки собираются все сразу, с путём до шага: `steps[2].on_yes[0] (change_stage): …`.
Коды выхода: `0` — успех, `1` — ошибки, `2` — неверные аргументы.

## 7. Разбор `.bpt` в спецификацию

`decompile file.bpt [--portal снимок] [--keep-names] [--json]`:
- шаги, на которые есть ссылки, получают читаемые `id` (`approve1`, `review3`); `{=A…:X}`
  переписывается в `{=@id:X}`;
- висячие ссылки сохраняются как есть, с предупреждением (их поймает `analyze`);
- свойства, равные значениям по умолчанию, опускаются — спецификация остаётся читаемой;
- со снимком известные коды заменяются плейсхолдерами: получается переносимая спецификация;
- типы и свойства вне каталога сохраняются (`raw`) с предупреждением;
- `--keep-names` добавляет `name` в каждый шаг — режим точной сверки.

## 8. Схема процесса

`render <file.bpt|spec.yaml> [-o схема.md]` → `flowchart TD` в блоке ```mermaid:
действия — прямоугольники, ожидания — с участниками, условия — ромбы с подписанными ветками,
параллельные ветки — развилка и слияние, цикл — обратная стрелка, блок — подграф, отключённые
шаги — пунктиром. Длинные тексты обрезаются. Спецификация с незаполненными плейсхолдерами рисуется
в режиме черновика.

## 9. Тесты

`php tools/bpt/tests/run.php [--corpus <папка с .bpt>]`.

**Синтетика (в репозитории):** пример «Согласование счёта» и пример снимка.
- сборка даёт ожидаемое дерево: свойства по умолчанию, разрешённые ссылки и плейсхолдеры,
  стабильные имена, нормализация значений YAML;
- разбор собранного и повторная сборка совпадают;
- схема содержит ожидаемые узлы;
- негативные фикстуры дают ожидаемые ошибки (неизвестный тип и свойство, нарушенная вложенность,
  повтор `id`, висячая ссылка, ненайденный плейсхолдер).

**Корпус (вне репозитория, путь через `--corpus`):**
- каталог покрывает все типы и свойства корпуса;
- `decompile --keep-names` → `compile` совпадает с оригиналом по смыслу: сравниваются канонические
  деревья (значения по умолчанию заполнены с обеих сторон, порядок ключей и служебный `Node`
  игнорируются);
- то же через снимок и плейсхолдеры;
- `render` отрабатывает на всех файлах.

Команды `decode`, `encode`, `check`, `analyze`, `compact` покрываются короткими регрессионными
проверками.

## 12. Критерии готовности блока

1. Каталог покрывает все 23 типа и все свойства корпуса — подтверждено тестом.
2. `decompile` → `compile` воспроизводит все 11 файлов корпуса по смыслу.
3. Пример спецификации собирается, проверяется и рисуется схемой; негативные фикстуры дают
   ожидаемые ошибки.
4. `SPEC.md`, `README.md` и страницы вики обновлены, записи в `log.md`, изменения закоммичены.
