# Playbook: миграция данных

> **Черновик — каркас.** Последовательность шагов отражает общую практику внедрения и уже
> накопленное в вики; конкретные цифры, инструменты и критерии приёмки команда проставляет после
> первого прогона на реальном проекте. Тогда же снимается `draft` и заполняется `verified`.

**Когда применять:** после [[checklist-presale-audit|аудита]] и фиксации требований, до запуска.
Объём и качество данных выясняются на аудите — если этого не сделали, начинать надо оттуда.

## Предусловия
- Известны источники: таблицы, прежняя CRM, учётная система, почта.
- Определена целевая структура: воронки, поля, смарт-процессы — иначе мигрировать некуда.
- Есть тестовый портал: **первый прогон миграции всегда на нём**.

## Чек-лист

### 1. Инвентаризация
- [ ] Перечислены все источники и объёмы (записей по каждой сущности)
- [ ] Для каждого источника известен способ выгрузки и её периодичность
- [ ] Отмечено, что мигрируем, а что оставляем в архиве источника
- [ ] Согласован **срок отсечки**: с какой даты данные считаются историческими

### 2. Качество данных до миграции
- [ ] Оценено количество дублей в источнике (по телефону, почте, названию)
- [ ] Определены правила нормализации: телефоны, адреса, названия компаний
- [ ] Обязательные поля целевой структуры покрыты данными источника — либо решено, чем заполнять
- [ ] Согласовано, что делать с записями без ответственного и без контактов

### 3. Соответствие полей
- [ ] Составлена карта «поле источника → поле Bitrix24» с типами
- [ ] Для списков и справочников сопоставлены **значения**, а не только поля
- [ ] Определено, куда уходит то, чему нет соответствия (служебное поле, комментарий, не переносим)
- [ ] Учтено, что коды пользовательских полей зависят от портала —
      [[recipe-smart-process-programmatic-creation|не зашивать их в скрипты]]

### 4. Пробный прогон
- [ ] Миграция выполнена на тестовом портале целиком, а не выборочно
- [ ] Сверены контрольные суммы: количество записей по каждой сущности
- [ ] Проверены связи: сделка ↔ контакт ↔ компания, вложения, ответственные
- [ ] Проверены граничные записи: самая старая, самая новая, с максимумом связей
- [ ] Заказчик посмотрел **свои** 10–20 записей и подтвердил, что это его данные

### 5. Техника загрузки
- [ ] Загрузка идёт [[pattern-rest-batch-and-limits|батчами]], а не по записи на запрос
- [ ] Повторный запуск **не создаёт дубли** — есть соответствие «внешний ключ → ID в портале»
      ([[pattern-rest-reliable-delivery]]). Внешний ключ — в своём пользовательском поле или своей
      таблице, **не** в `ORIGINATOR_ID`/`ORIGIN_ID`: они заполняются только при создании из внешней
      системы и не годятся как ключ синхронизации («Книга разработчика», поля лида/контакта/компании/
      сделки, коробка)
- [ ] Автоматизация на время загрузки **выключена**: роботы и бизнес-процессы не должны
      срабатывать на исторических записях
- [ ] Уведомления отключены — иначе сотрудники получат тысячи писем о «новых» сделках
- [ ] Коробка, загрузка кодом: у старого API CRM для этого есть опции `REGISTER_SONET_EVENT`,
      `IS_SYSTEM_ACTION`, `DISABLE_TIMELINE_CREATION` и др., у операций Universal API —
      `disableBizProc()`/`disableAutomation()` (`disableAllChecks()` их **не** выключает) —
      [[recipe-crm-legacy-entity-crud]], [[entity-crm-operation]]
- [ ] Ведётся журнал: что загружено, что отклонено и почему

### 6. Боевая миграция
- [ ] Согласовано окно и кто на связи с обеих сторон
- [ ] Сделана резервная копия портала до загрузки
- [ ] Источник на время загрузки заморожен либо определён порядок довыгрузки «хвоста»
- [ ] После загрузки автоматизация и уведомления включены обратно
- [ ] Выполнена повторная сверка контрольных сумм

## Критерии приёмки
- Количество записей по каждой сущности совпадает с согласованным.
- Ответственные проставлены, связи не потеряны.
- Заказчик подтвердил выборку записей письменно.
- Повторный запуск загрузчика не меняет состояние портала.

## Частые ошибки
- Мигрировать до того, как утверждена структура: переделывать придётся всё.
- Тащить «всё как есть» вместе с мусором — дубли и пустые записи потом дискредитируют систему в
  глазах пользователей.
- Забыть выключить автоматизацию: роботы отработают на исторических сделках и разошлют клиентам
  письма.
- Сверять только итоговое количество и не проверять связи.
