# Playbook: рабочая встреча по требованиям

**Когда применять:** после [[checklist-presale-audit|предпроектного аудита]] и на любых
последующих встречах, где обсуждаются конкретные процессы. Цель — чтобы после встречи осталась
структура, с которой можно работать, а не аудиозапись и три страницы заметок.

## Предусловия
- Известны участники и их роли: кто заказчик решения, кто носитель процесса, кто принимает
  решение по спорным пунктам.
- Прочитаны материалы предыдущих встреч по этому же процессу.

## Разбор встречи — семь файлов

Результат каждой встречи раскладывается по назначению. Это не бюрократия: разделение нужно, чтобы
**требование не путалось с решением, а решение — с задачей**.

| Файл | Что туда идёт |
|---|---|
| `00_context.md` | общий контекст и текущее состояние: что уже есть на портале, что обсуждали раньше |
| `01_requirements.md` | требования — пронумерованные, по подсистемам, формулировкой заказчика |
| `02_decisions.md` | принятые решения **и отклонённые варианты с причиной** |
| `03_tasks.md` | задачи и ответственные (с обеих сторон) |
| `04_open_questions.md` | вопросы, требующие решения; каждый — с тем, кто отвечает |
| `05_technical_details.md` | технические правила и ограничения, всплывшие на встрече |
| `06_source_notes.md` | исходные заметки или расшифровка — источник, к которому можно вернуться |

Спецификации отдельных расчётов (формулы, структура выгрузки) выносятся в свои файлы рядом.

## Чек-лист

### До встречи
- [ ] Перечитаны материалы прошлых встреч по теме
- [ ] Подготовлен список открытых вопросов с прошлого раза
- [ ] Ясно, какое решение нужно получить на этой встрече

### На встрече
- [ ] Каждое требование зафиксировано **словами заказчика**, не пересказом
- [ ] Для каждого спорного пункта записано не только решение, но и **что отклонили и почему**
- [ ] Отмечено, что именно **не обсудили** — это станет открытым вопросом, а не пропадёт
- [ ] У каждой задачи есть ответственный с обеих сторон и срок
- [ ] Для доработки коробки задан вопрос **«модулем или нет?»** —
      [[pattern-module-based-development-standard]]
- [ ] Для автоматизации задан вопрос **«робот или бизнес-процесс?»** —
      [[pattern-robots-vs-bizproc-decision]]

### После встречи
- [ ] Материалы разложены по семи файлам выше
- [ ] Противоречия между структурированным описанием и исходными заметками **выписаны явно**,
      а не сглажены
- [ ] Отсутствующие требования не додуманы: где не хватает информации — сказано, чего именно
- [ ] Протокол отправлен участникам, зафиксирована дата ответа по открытым вопросам

## Правила работы с этими материалами

Три правила, которые и делают разбор полезным:

1. **Не выдумывать отсутствующие требования.** Пробел — это открытый вопрос, а не повод
   достроить логику за заказчика.
2. **Противоречие между структурированным описанием и исходными заметками указывать явно.**
   Молча выбранная трактовка всплывёт на приёмке.
3. **Не хватает информации для реализации — сначала обозначить, чего именно не хватает**, и
   только потом предлагать варианты.

Те же правила применимы, когда материалы встречи читает агент: структура даёт ему возможность
сверяться с требованиями, а не пересобирать их из расшифровки заново.

## Критерии приёмки
- По материалам встречи можно поставить задачу разработчику, не задавая уточняющих вопросов
  участникам.
- Через месяц по `02_decisions.md` понятно, **почему** выбрали этот вариант.
- Ни один пункт не остался в статусе «вроде договорились».

## Частые ошибки
- Всё в одном документе: требования смешаны с решениями, через две встречи не найти, что уже
  утверждено.
- Отклонённые варианты не записаны — на следующей встрече обсуждаются заново.
- Открытые вопросы без ответственного: висят до приёмки.
- Требование записано как решение («сделать поле обязательным») — теряется исходная задача, и
  лучший вариант решения уже не рассмотреть.
