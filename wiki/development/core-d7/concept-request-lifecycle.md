# Жизненный цикл HTTP-запроса

**TL;DR:** запрос проходит две фазы — выбор файла по URI и исполнение страницы. Знание пайплайна
отвечает на три вопроса: где доступен `$USER`, куда вешать обработчик и почему консольный скрипт
ведёт себя иначе.

## Фаза A. Выбор файла

1. **Физический файл существует?** — подключается напрямую, фаза завершена.
2. **Есть правило в `urlrewrite.php`?** — подключается `/bitrix/urlrewrite.php`, в `$arUrlRewrite`
   ищется первое подходящее правило (по `SORT`, затем по длине условия), подключается файл из
   `PATH` с подменой параметров.
3. **Ни того, ни другого** — подключается `/404.php`.

Исторически **все «маршруты» продукта проходят через 404** — это штатный механизм, а не ошибка.
Ключевое следствие: **единой точки входа нет**, в отличие от классических MVC-фреймворков.

## Фаза B. Исполнение страницы

Каноническая страница — `require .../bitrix/header.php` → тело → `require .../bitrix/footer.php`.
Внутри разворачивается пайплайн; узловые точки:

| Шаг | Что происходит |
|---|---|
| — | Служебная часть пролога (`prolog_before.php`) |
| 1–2 | `dbconn.php`, соединение с БД (здесь падает `(2002) Connection refused` — [[recipe-mysql-connection-refused]]) |
| 3 | `after_connect.php`, `after_connect_d7.php` |
| 4 | `$APPLICATION`, `SITE_ID`, `SITE_DIR`, `LANGUAGE_ID`, загрузка главного модуля |
| 5 | **`/local/php_interface/init.php`** (или `/bitrix/php_interface/init.php`) |
| 6 | `init.php` конкретного сайта |
| 7 | Открытие сессии |
| 8 | Событие **`OnPageStart`** |
| 9 | Определение и авторизация пользователя — **`$USER` доступен с этого момента** |
| 10 | Определение `SITE_TEMPLATE_ID` |
| 11 | Событие **`OnBeforeProlog`** |
| 12 | Проверка прав на физический файл; нет прав — форма авторизации, страница завершается |
| 13 | **Старт буферизации вывода** |
| 14 | Событие **`OnProlog`** |
| 15–16 | Визуальная часть пролога, `header.php` шаблона |
| 17 | **Тело страницы** |
| 18–19 | Визуальная часть эпилога, `footer.php` шаблона |
| 21 | Служебный эпилог; **здесь выполняются отложенные функции** (`AddBufferContent`, `ViewTarget`) |
| 22 | Событие **`OnEpilog`** |
| 23 | Завершение буферизации, вывод в поток |
| 24 | Событие **`OnAfterEpilog`** |
| 25 | Фоновые работы: проверка агентов, отправка почты |
| 26 | Закрытие соединения с БД |

## Что из этого следует на практике

- **`init.php` подключается до `OnPageStart`** — поэтому обработчики событий регистрируют именно
  там ([[pattern-events-over-core-modification]]), и туда же модуль вписывает свою загрузку
  ([[recipe-d7-orm-event-subscription]]).
- **`$USER` не существует раньше шага 9.** Код в `init.php`, который рассчитывает на текущего
  пользователя, получит пустоту — частая причина «на проде работает, в агенте нет».
- **Буферизация с 13 по 23** — весь HTML копится и выливается одним куском. На этом стоит механизм
  отложенных функций: вывод, «дорисовываемый» на шаге 21.
- **Агенты выполняются в фоновых работах после отдачи страницы** — отсюда их плавающее время
  запуска и потолок по длительности ([[pattern-agents-vs-cron]]).
- **Консольный и cron-режим — не этот пайплайн.** Нет `$USER`, нет сессии, нет `$_SERVER`,
  часть статистики и прав отключается вручную. Отсюда же требование запускать консольный PHP от
  владельца сайта ([[antipattern-cli-php-as-root]]).

## Почему важно при внедрении

Пайплайн — карта точек расширения. Выбор уровня в
[[concept-change-invasiveness-hierarchy|иерархии способов изменения]] почти всегда сводится к
вопросу «на каком шаге я могу вмешаться, не трогая продукт».
