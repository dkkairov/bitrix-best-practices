# Жизненный цикл HTTP-запроса

**TL;DR:** запрос проходит две фазы — выбор файла по URI и исполнение страницы. Знание пайплайна
отвечает на три вопроса: где доступен `$USER`, куда вешать обработчик и почему консольный скрипт
ведёт себя иначе. Источник — «Книга разработчика»:
[Обработка uri](https://bx24devbook.website.yandexcloud.net/Obsie_svedenia/Obrabotka_uri.html),
[Страница](https://bx24devbook.website.yandexcloud.net/Obsie_svedenia/Stranica.html).

> **Сверено с книгой 2026-09-21.** Уточнены: фаза A (каталог и симлинк, где лежат правила ЧПУ), шаг 4
> (заранее заданный `SITE_ID`), нумерация (в книге после 25 идёт 27), агенты (зависят от версии и
> режима запуска, «потолка по длительности» в книге нет) и консольный режим (служебный пролог в
> CLI выполняется). Закрыт открытый вопрос про `OnPageStart` / `OnBeforeProlog` / `OnProlog`.

## Фаза A. Выбор файла

1. **Существует физический файл, каталог (если файла нет или это `index.php`) или символьная
   ссылка?** — подключается напрямую, фаза завершена.
2. **Есть правило ЧПУ?** — подключается обработчик `/bitrix/urlrewrite.php`; правила — массив
   `$arUrlRewrite` в файле `urlrewrite.php`, отсортированный по `SORT`, при равной сортировке — по
   длине условия ([[entity-urlrewrite]]). Найдено правило — подключается файл из `PATH` с подменой
   параметров.
3. **Ни того, ни другого** — подключается `/404.php`.

Исторически **все «маршруты» продукта проходят через 404** — это штатный механизм, а не ошибка.
Ключевое следствие: **единой точки входа нет**, в отличие от классических MVC-фреймворков.

## Фаза B. Исполнение страницы

Каноническая страница — `require .../bitrix/header.php` → тело → `require .../bitrix/footer.php`.
Внутри разворачивается пайплайн; нумерация — как в книге
([порядок выполнения](https://bx24devbook.website.yandexcloud.net/Obsie_svedenia/Stranica.html#poradok-vypolnenia)):

| Шаг | Что происходит |
|---|---|
| — | Служебная часть пролога (`prolog_before.php`) |
| 1–2 | `dbconn.php`, соединение с БД (здесь падает `(2002) Connection refused` — [[recipe-mysql-connection-refused]]) |
| 3 | `after_connect.php`, `after_connect_d7.php` (каждый — при наличии) |
| 4 | `$APPLICATION`, `SITE_ID`, `SITE_DIR`, `LANGUAGE_ID`, загрузка главного модуля. **Если `SITE_ID` определён заранее, сайт по папке и домену не определяется** |
| 5 | **`/local/php_interface/init.php`** (или `/bitrix/php_interface/init.php`) |
| 6 | `/bitrix/php_interface/<ID сайта>/init.php` |
| 7 | Открытие сессии |
| 8 | Событие **`OnPageStart`** |
| 9 | Определение и авторизация пользователя — **`$USER` доступен с этого момента** |
| 10 | Определение `SITE_TEMPLATE_ID` |
| 11 | Событие **`OnBeforeProlog`** |
| 12 | Проверка прав на физический файл; нет прав — форма авторизации, страница завершается |
| 13 | **Старт буферизации вывода** |
| 14 | Событие **`OnProlog`** |
| 15–16 | Визуальная часть пролога, `header.php` шаблона |
| 17 | **Тело страницы** |
| 18–19 | Визуальная часть эпилога, `footer.php` шаблона |
| 20 | `CMain::ShowSpreadCookieHTML` (перенос посетителей между доменами) |
| 21 | Служебная часть эпилога; **здесь выполняются отложенные функции** — [[concept-deferred-functions-and-page-areas]] |
| 22 | Событие **`OnEpilog`** |
| 23 | Завершение буферизации, вывод в поток |
| 24 | Событие **`OnAfterEpilog`** |
| 25 | Фоновые работы: проверка агентов, отправка почты |
| 27 | Закрытие соединения с БД (в книге номер 26 пропущен) |

## Что из этого следует на практике

- **`init.php` подключается до `OnPageStart`** — поэтому подписки на события подключают именно
  оттуда ([[pattern-events-over-core-modification]]), и туда же модуль вписывает свою загрузку
  ([[recipe-d7-orm-event-subscription]]).
- **`$USER` не существует раньше шага 9.** Код в `init.php`, который рассчитывает на текущего
  пользователя, получит пустоту.
- **Три события пролога различаются тем, что уже известно:** `OnPageStart` (8) — сессия есть,
  пользователя и шаблона ещё нет; `OnBeforeProlog` (11) — есть `$USER` и `SITE_TEMPLATE_ID`, но права
  на файл ещё не проверены и буфер не начат; `OnProlog` (14) — права проверены, буферизация идёт.
- **Буферизация с 13 по 23** — весь HTML копится и выливается одним куском. На этом стоит механизм
  отложенных функций: вывод «дорисовывается» в служебной части эпилога (шаг 21).
- **Агенты.** С главного модуля 20.5.0 агенты и почта — фоновые работы после отдачи страницы (шаг 25);
  до 20.5.0 они выполнялись в начале хита, до сессии и `OnPageStart`. Так — в режиме «на хитах»;
  агенты можно перевести на cron целиком или частично (комбинированный режим). Отсюда плавающее время
  запуска на хитах; своего «потолка по длительности» у агентов книга не называет — есть
  однопоточность и блокировка — [[pattern-agents-vs-cron]].
- **Консольный и cron-режим.** Скрипт подключает `prolog_before.php`, поэтому **служебный пролог
  выполняется** — `init.php` и обработчики событий срабатывают. Но пользователь — гость, сессии и
  cookie нет, `$_SERVER` не заполнен веб-сервером; в конце обязателен `\CMain::FinalActions()` —
  [[recipe-cli-script-bootstrap]]. Консольный PHP запускаем от владельца сайта (опыт команды —
  [[antipattern-cli-php-as-root]]).

## Почему важно при внедрении

Пайплайн — карта точек расширения. Выбор уровня в
[[concept-change-invasiveness-hierarchy|иерархии способов изменения]] почти всегда сводится к
вопросу «на каком шаге я могу вмешаться, не трогая продукт».
