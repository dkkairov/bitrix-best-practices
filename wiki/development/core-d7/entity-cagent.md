# `CAgent`

**Что это:** управление агентами — записями таблицы `b_agent`, чей PHP-код исполняется по
расписанию. Старый C-API; D7-эквивалента в книге нет. Источник —
[Агенты](https://bx24devbook.website.yandexcloud.net/Razrabotka/Tehnologii/Agenty.html) «Книги
разработчика».

> **Сверено с книгой 2026-09-21.** Исправлено: «не вызывает `Delete` внутри» книга говорит про
> `RemoveAgent`, а не про `RemoveModuleAgents`; убрано не подтверждённое книгой утверждение о
> побочных действиях. Добавлены периодичность, режимы запуска, ограничения и отладка.

## Ключевые факты
| Поле | Значение |
|------|----------|
| Тип | класс со статическими методами |
| Модуль | `main` |
| Хранилище | `b_agent`, поле кода до 64 КБ |
| Исполнение | `eval`, код **обязан вернуть строку** |
| Точка запуска | с main 20.5.0 — фоновые работы после отдачи страницы (режим «на хитах»); до 20.5.0 — в начале хита, до сессии и `OnPageStart`; возможен запуск от cron ([[concept-request-lifecycle]]) |

## Создание

```php
\CAgent::AddAgent(
    "\\Vendor\\Module\\Agent::run();",   // код одной строкой, точка с запятой обязательна
    'vendor.module',                     // модуль
    'N',                                 // периодический ли — см. ниже, по умолчанию N
    86400                                // интервал, секунд
);
```

`AddAgent` — обёртка над `Add`, проверяет дубли по паре «имя + пользователь»: повторный вызов не
создаст второй агент, а вернёт `false`. Низкоуровневый `CAgent::Add($arFields)` использовать не
рекомендуется. Дальнейшие параметры `AddAgent`: дата первой проверки, активность, время первого
запуска, сортировка, пользователь.

**Код агента пишется одной строкой — вызовом функции или статического метода.** Логика живёт в
классе, а не в строке в базе: иначе её нельзя ни отладить, ни положить в репозиторий.

**Возврат обязателен:** пустая строка — не повторять, имя следующего агента — поставить его в
очередь.

## Периодический или непериодический

| Вид | Следующий запуск | После пропусков |
|-----|------------------|-----------------|
| Периодический (`'Y'`, «точно в указанное время») | прежнее назначенное время + интервал | выполнится **столько раз, сколько пропустил** |
| Непериодический (`'N'`, «через интервал») | время завершения прошлого запуска + интервал | выполнится **один раз** |

Абсолютное большинство агентов — непериодические. На малопосещаемом портале достаточно нескольких
периодических агентов, чтобы пролог страниц занимал почти всё время генерации: система пытается
догнать пропуски. Лечение по книге — выключить периодичность
([периодические агенты](https://bx24devbook.website.yandexcloud.net/Razrabotka/Tehnologii/Agenty.html#periodiceskie-agenty)).

## Режимы запуска
- все агенты на хитах;
- все агенты на cron;
- комбинированный: непериодические на cron, периодические на хитах — по умолчанию в Bitrix Env.

Выбор между агентом и cron-скриптом — [[pattern-agents-vs-cron]].

## Ограничения исполнения
- Нет `$USER` (даже глобальная `$USER` не гарантирует объект `CUser`) — код, проверяющий права,
  должен уметь их отключать.
- Нет `SITE_ID`: агент может выполниться на любой странице, в админке и в CLI; язык заранее неизвестен.
- Однопоточность с блокировкой в MySQL на 10 минут: новый запуск — только после завершения
  предыдущего.
- На хитах точность зависит от посещаемости; для точного времени — cron.
- Нельзя `Authorize` — cookie авторизации уйдут случайному посетителю.

## Обновление и удаление

| Метод | Что делает |
|---|---|
| `Update($agentId, $arFields)` | единственный способ изменить (низкоуровневый) |
| `RemoveAgent($name, $module, $user_id)` | удалить по имени, с ограничением по модулю и пользователю; `Delete` внутри не вызывает |
| `Delete($id)` | удалить по ID |
| `RemoveModuleAgents($module)` | удалить **все** агенты модуля — обязательный шаг в `DoUninstall` |

## Выборка: `GetList($arOrder, $arFilter)`

Только порядок и фильтр — ни пагинации, ни выбора полей, ни сложной логики. `GetById` — обёртка над
`GetList`.

| Ключ фильтра | Поведение |
|---|---|
| `ID`, `MODULE_ID`, `=NAME` | строгое сравнение |
| `NAME` | LIKE |
| `ACTIVE`, `IS_PERIOD` | `Y`/`N`; иное значение игнорируется |
| `USER_ID` | `> 0` — по пользователю; иначе — агенты без пользователя (в книге рядом есть оговорка, что ключ может не обрабатываться, — проверить на своей версии) |
| `LAST_EXEC` | дата в формате `CLang::GetDateFormat()` |
| `NEXT_EXEC` | дата в формате `FORMAT_DATETIME` |

## Отладка

Функция-логгер с сигнатурой `($arAgent, $strEvent, $strEvalResult = null, $error = "")` и константа
`BX_AGENTS_LOG_FUNCTION` с её именем; события — `start`, `finish`, `not_callable`. Функцию удобно
держать в `legacy.php` ([[pattern-local-solution-structure]]). **Оговорка книги:** в релизах 21–22
при исключении в агенте события `finish` и `not_callable` не вызываются — смотреть лог исключений
главного модуля; на актуальной версии перепроверить
([отладка агентов](https://bx24devbook.website.yandexcloud.net/Razrabotka/Tehnologii/Agenty.html#otladka-agentov)).

## Подводные камни

- **`LAST_EXEC` и `NEXT_EXEC` принимают разные форматы дат.** В многосайтовых и кластерных
  конфигурациях форматы могут отличаться — легко получить пустую выборку вместо ошибки.
- **Пустая строка в ключе фильтра просто игнорируется** — условие исчезает, и вы получаете больше
  строк, чем ждали.
- **Периодичность `'Y'` без необходимости** — перегрузка малопосещаемого портала (см. выше).
- Агент — не место для тяжёлых операций: см. [[pattern-agents-vs-cron]].
- Забыть снять агенты в `DoUninstall` — классический «мусор после удаления модуля»
  ([[recipe-module-structure-and-install]]).
