# Агенты или cron

> **Исправлено 2026-09-21 при сверке с «Книгой разработчика».** Правило 3 говорило «нужна точность
> до минуты и лучше → агент» — это обратно книге: для **точного времени** она велит cron, а агент
> выбирают, когда нужен **интервал меньше минуты**. Убран «жёсткий потолок по длительности» агентов
> (в книге — однопоточность и блокировка); добавлены режимы запуска и периодичность. Правило 4
> размечено как практика команды: книга по умолчанию рекомендует агенты
> ([Агенты](https://bx24devbook.website.yandexcloud.net/Razrabotka/Tehnologii/Agenty.html#vybor-mezdu-agentami-i-cron)).

## Проблема и контекст

Нужен повторяющийся фоновый PHP-код: рассылка, синхронизация, пересчёт. В коробке два штатных
способа — агенты Bitrix и системный cron. Вопрос всплывает на каждом проекте, поэтому решение
стоит принимать по таблице, а не по привычке.

## Сравнение

| Аспект | Агенты (`CAgent`) | cron-скрипт |
|---|---|---|
| Где живёт | таблица `b_agent` | расписание ОС (`crontab`) |
| Где выполняется | с main 20.5.0 — фоновые работы после отдачи страницы (режим «на хитах»); либо от cron — см. режимы ниже | вне HTTP, отдельный процесс PHP |
| Точность времени | на хитах зависит от посещаемости: запуск — когда кто-то открыл страницу | строгая, по расписанию ОС |
| Минимальный интервал | меньше минуты | 1 минута |
| Контекст Bitrix | без `$USER`, без `SITE_ID`, язык неизвестен | константы + `prolog_before.php`, пользователь — гость ([[recipe-cli-script-bootstrap]]) |
| Тиражируемость | **переезжает вместе с модулем** | нужен доступ к ОС у клиента |
| Тяжёлые задачи | нет: агенты однопоточны, с блокировкой в MySQL на 10 минут | да, можно `set_time_limit(0)` |
| Сложность настройки | низкая (вызов API) | средняя (SSH, права, владелец процесса) |

**Режимы запуска агентов** (книга): все на хитах; все на cron; комбинированный — непериодические на
cron, периодические на хитах (по умолчанию в Bitrix Env).

## Правила выбора

1. **Тяжёлая операция** (5+ секунд или много памяти) → **cron**.
2. **Тиражируемый модуль** (ставится на чужие порталы) → **агент**: на чужой установке cron не
   настроишь.
3. **Нужен интервал меньше минуты** → **агент** (cron не умеет); **нужно точное время запуска** →
   **cron** (агент на хитах срабатывает позже, по первому посещению).
4. **Остальное.** Книга советует агенты, оговаривая, что это вкусовщина, а сам автор предпочитает
   cron. **Практика команды:** база — cron для проектной работы, агенты — там, где логика обязана
   переехать вместе с модулем или нужен интервал меньше минуты.

## Когда агент точно нельзя
- Авторизация пользователя внутри агента (`Authorize`) — отправит cookie случайному посетителю.
- Нужен гарантированно точный момент времени.
- Операция дольше ~5 секунд.

## Когда cron точно нельзя
- У клиента нет доступа к ОС (shared-хостинг).
- Интервал меньше минуты.
- Логика должна переехать вместе с модулем.

## Как реализовать

```php
// агент: раз в сутки, НЕпериодический ('N') — при пропусках выполнится один раз
\CAgent::AddAgent('\\Vendor\\Module\\Agent::run();', 'vendor.module', 'N', 86400);
```

Периодический агент (`'Y'`) догоняет каждый пропущенный запуск: на малопосещаемом портале
нескольких таких агентов хватает, чтобы пролог страниц занимал почти всё время генерации. По
умолчанию ставим `'N'` — [[entity-cagent]].

```bash
# cron: от владельца сайта, НЕ от root
*/5 * * * * bitrix /usr/bin/php -f /home/bitrix/www/local/php_interface/console/sync.php >> /var/log/sync.log 2>&1
```

Скелет самого скрипта (константы, `prolog_before.php`, `\CMain::FinalActions()` в конце) —
[[recipe-cli-script-bootstrap]]. Владелец процесса критичен: консольный PHP с ядром от root портит
кэш портала — [[antipattern-cli-php-as-root]].

## Последствия
- **Агенты:** ноль требований к инфраструктуре, но плавающее время запуска на малопосещаемых
  порталах; однопоточность и блокировка — тяжёлое не вешать.
- **cron:** предсказуемость и отсутствие ограничений по времени ценой доступа к серверу и
  отдельной процедуры переноса при миграции портала.

## Открытые вопросы
- Интервалы между 1 секундой и 1 минутой на малопосещаемом портале: агент на хитах теряет
  точность, cron не умеет — чем закрывать.
- Комбинированный режим (непериодические агенты на cron) — по умолчанию в Bitrix Env; детали
  настройки — в официальном уроке «Запуск агентов», на который ссылается книга.
