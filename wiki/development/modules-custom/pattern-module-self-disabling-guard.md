# Сторож модуля: портал важнее модуля

## Проблема и контекст

Модуль вмешивается в горячий путь портала: подменяет фабрику CRM, висит на событии сохранения,
подключает JS в карточку. Любая его ошибка становится ошибкой **портала**, а не модуля: люди не
могут сохранить сделку, а админ видит белый экран и не понимает, кто виноват.

Отдельный риск — обновление продукта. Наш класс наследует ядровый (`Factory\Dynamic`). Если в
новой версии Bitrix изменится сигнатура переопределяемого метода, PHP выдаст **фатал на всём
портале** при первом же хите — ещё до того, как наш код что-то сделает.

Требование заказчика формулируется просто: «Битрикс должен работать всегда; если ломается ваш
модуль — пусть выключается сам и скажет админу».

## Решение

Три уровня защиты, потому что ловятся разные вещи.

| Уровень | Что ловит | Механизм |
|---|---|---|
| 1 | Исключение в нашем коде | `try/catch` на месте; сохранение элемента продолжается как ни в чём не бывало |
| 2 | Фатал PHP в наших файлах | `register_shutdown_function` — фатал через `try/catch` не ловится |
| 3 | Несовместимость с ядром | сверка сигнатур рефлексией **до** объявления наших классов; фатала не происходит вообще |

Во всех трёх случаях исход один: `Option::set(<module>, 'enabled', 'N')`. На следующем хите
`include.php` выходит сразу — фабрики не подменяются, JS не подключается, портал работает из
коробки.

## Как реализовать

### Уровень 2 — фатал в наших файлах

```php
register_shutdown_function(static function (): void {
    $e = error_get_last();
    if (!$e || !in_array($e['type'], [E_ERROR, E_PARSE, E_CORE_ERROR, E_COMPILE_ERROR], true)) {
        return;
    }
    // чужие фаталы — не наше дело
    if (strpos($e['file'], __DIR__) !== 0) {
        return;
    }
    Guard::panic('fatal: ' . $e['message'] . ' @ ' . $e['file'] . ':' . $e['line']);
});
```

Проверка «файл ошибки внутри каталога модуля» обязательна: без неё модуль будет выключать себя
из-за чужих падений.

### Уровень 3 — сверка сигнатур до объявления класса

```php
// Registrar::isCompatible() — вызывается ДО require нашего наследника
$ref = new \ReflectionMethod(\Bitrix\Crm\Service\Factory::class, 'getUpdateOperation');
if ($ref->isFinal()) return false;

$params = $ref->getParameters();
if (count($params) !== 2) return false;
if ((string)$ref->getReturnType() !== \Bitrix\Crm\Service\Operation\Update::class) return false;
```

Не совпало → отдаём штатную фабрику, `Guard::panic()`, красная плашка в админке. Портал даже не
замечает происходящего.

### Уведомление — ровно один раз

Сообщение уходит на переходе «работал → выключен», а не на каждом хите. Получатель задаётся в
настройках модуля; не задан — активные администраторы портала.

```php
public static function panic(string $reason): void
{
    if (Option::get(self::MODULE_ID, 'enabled', 'Y') === 'N') return;  // уже выключены — молчим
    Option::set(self::MODULE_ID, 'enabled', 'N');
    self::notifyAdmins($reason);
}
```

## Когда применять
- Модуль подменяет ядровый сервис или наследует ядровый класс.
- Модуль работает в горячем пути: сохранение сущности, сборка меню, рендер карточки.
- Модуль ставится на прод, где нет окна для отладки.

## Когда НЕ применять
- Изолированная админ-страница или отчёт: падение видно там же и портал не задевает — сторож
  только добавит сложности.

## Последствия
- **Плюсы:** обновление продукта не роняет портал; инцидент локализован и виден админу; модуль
  можно ставить на прод без окна обслуживания.
- **Минусы:** модуль может «тихо выключиться» и никто не заметит, что функция не работает —
  поэтому уведомление обязательно, а плашка в админке желательна. Плюс рефлексия добавляет
  несколько миллисекунд на хит (кэшируется в `Option`).

## Что не делать
- Не выключать модуль на **некритичных** сбоях (не подключился JS): серверная проверка важнее,
  тут достаточно предупреждения не чаще раза в час.
- Не полагаться на `try/catch` для фаталов — он их не видит.
- Не проверять совместимость **после** объявления класса: к этому моменту фатал уже произошёл.
