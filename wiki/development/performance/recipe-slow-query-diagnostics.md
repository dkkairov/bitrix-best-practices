# Найти и вылечить медленные запросы

**Результат:** понятно, какие запросы съедают время страницы, откуда в коде они пришли и что с ними
делать.

**Когда применять:** страница или агент тормозит, а профилировать «на глаз» не хочется. Прежде чем
накрывать проблему кэшем ([[concept-box-caching]]) — сначала сюда.

## Шаг 1. Что именно выполняется

```php
use Bitrix\Main\Application;

$conn = Application::getConnection();
$conn->startTracker(true);          // true — сбросить накопленное

// ... подозрительный код ...

$conn->stopTracker();
$tracker = $conn->getTracker();

echo $tracker->getCounter() . ' запросов за ' . round($tracker->getTime(), 4) . " с\n";
foreach ($tracker->getQueries() as $q)
{
    echo round($q->getTime(), 4) . ' с — ' . $q->getSql() . "\n";
    print_r($q->getTrace());        // откуда вызвано
}
```

Проверено на стенде: две выборки ORM дали `getCounter() = 2`, время по каждой, полный SQL и по
4 кадра трассировки; глубина трассировки по умолчанию — 10 кадров, меняется
`setDepthBackTrace()`. Писать в файл вместо вывода — `startFileLog($path)` / `stopFileLog()`.

## Шаг 2. Штатные инструменты админки

- **Монитор производительности** (Настройки → Производительность) — общая картина: время хита,
  число запросов, самые тяжёлые страницы.
- **«Записывать только медленные SQL-запросы»** — порог по умолчанию **0,1 с**.
- **Анализ индексов** в том же разделе — подсказывает недостающие.

## Шаг 3. Приёмы, которые дают эффект

| Симптом | Что делать |
|---|---|
| запрос **в цикле** (N+1) | собрать идентификаторы в массив и сделать один запрос с фильтром `@ID` |
| выбирается **вся сущность** ради одного поля | `getList` с явным `select` вместо `GetByID`: `CIBlockElement::GetByID()` тянет все поля |
| фильтр по **`LIKE`** | точное сравнение: в фильтре ORM ключ без префикса даёт `UPPER() LIKE upper()`, поэтому пишем `'=FIELD' => $v` ([[concept-d7-orm-query]]) |
| связанные данные **отдельными запросами** | `runtime`-связь или `Reference`/`OneToMany` и один запрос с `join` ([[concept-d7-orm-relations]]) |
| фильтр по нескольким полям **без индекса** | составной индекс — один индекс сразу по нескольким колонкам, порядок колонок важен |
| универсальный метод там, где есть специализированный | у модулей есть узкие методы (например, установка оплаты в «Продажах» вместо общего `setFields`) |

## Шаг 4. Что померить после

Тот же трекер до и после правки: число запросов и суммарное время. Если запросов стало меньше, а
время не изменилось — проблема в самом запросе (план, индексы), а не в их количестве.

## Подводные камни

- **Трекер считает только SQL.** Время ушло в PHP или во внешний сервис — он этого не покажет.
- **Трассировка стоит денег.** На проде включать точечно и выключать — `stopTracker()`.
- **Индекс не бесплатный:** ускоряет чтение, замедляет запись и занимает место. Индексы под разовый
  отчёт — плохая сделка.
- **Кэш поверх медленного запроса** прячет проблему до первого сброса кэша, а сбросится он в самый
  неудачный момент.
