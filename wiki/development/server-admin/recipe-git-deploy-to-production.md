# Доставка правки на прод через git

**Результат:** локальная правка доехала до прода, чужая работа не затёрта, на каждом шаге есть
откат. Прод всегда едет на стабильной ветке `main`.

> Делать строго сверху вниз. Увидел непонятное или слово **`CONFLICT`** — остановись и разберись,
> не гони дальше.

## Предусловия
- Рабочий каталог портала на сервере — клон репозитория, прод тянет **только** `main`.
- Разработчик работает в своей ветке (`task/<слаг>`), прямо в `main` не коммитит.
- Доступ по SSH к серверу (при необходимости — через VPN).

## Шаги

### Шаг 0 (один раз перед началом) — страховочная закладка
```bash
git status                      # убедиться, что на своей рабочей ветке
git branch backup/ГГММДД-before # «фотка» ветки; ничего не меняет
```
Если позже что-то пойдёт не так: `git reset --hard backup/ГГММДД-before`.

### Шаг 1 — закоммитить правку
```bash
git add путь/к/файлу.php        # или git add -A
git commit -m "Короткое описание, что изменил"
```
Рабочая директория должна стать чистой — это важно перед следующим шагом.

### Шаг 2 — подтянуть чужие изменения в свою ветку
```bash
git fetch origin
git merge origin/main
```
Исходы:
- `Merge made…` или `Already up to date.` → хорошо, дальше.
- **Открылся редактор** (текст «Merge remote-tracking branch…») → ничего не меняя,
  `Shift+Z Shift+Z`. Запасной вариант: `Esc`, затем `:wq`, `Enter`.
- **`CONFLICT`** → стоп, не пушить. Разобрать, чтобы не потерять ни своё, ни чужое.
  Аварийный откат слияния: `git merge --abort`.

### Шаг 3 — залить ветку
```bash
git push origin <имя-твоей-ветки>
```

### Шаг 4 — Pull Request в `main`
1. Открыть PR из своей ветки; проверить направление: `base: main` ← `compare: <твоя ветка>`.
2. Create pull request → Merge pull request → Confirm merge.
3. Ветку после мержа **не удалять** — пригодится для отката и истории.

Если жёлтая плашка «recent pushes» пропала (живёт пару минут) — прямая ссылка на сравнение:
`https://<хост-репозитория>/<владелец>/<репозиторий>/compare/main...<твоя-ветка>`.

### Шаг 5 — подтянуть на прод
```bash
ssh <пользователь>@<адрес-сервера>
cd /home/bitrix/www
git branch                     # убедиться, что активна main
git pull
```
Ждём `Fast-forward` и список обновлённых файлов.

## Проверка результата
- На сервере `git log -1` показывает ваш коммит.
- Затронутая функциональность работает на портале.
- Новый модуль, приехавший через pull, **установлен** (см. ниже) — файлы на диске ≠ установленный
  модуль.

## Откат и проблемы

| Ситуация | Что делать |
|---|---|
| `git pull` на сервере: «local changes would be overwritten» | На проде правили файлы в обход git (Bitrix сам правит, например, `.top.menu_ext.php`). `git stash push -- <файлы>` → `git pull` → `git stash pop`. `stash` не удаляет, а прячет и возвращает |
| `push` отбился `rejected (non-fast-forward)` | На удалённой ветке появились чужие коммиты. Это защита: повторить шаг 2 (`fetch` + `merge origin/main`), затем `push` |
| Нужно откатить свою ветку | `git reset --hard backup/ГГММДД-before` |
| Незавершённое слияние | `git merge --abort` |
| Нужно откатить смерженный PR | Кнопка **Revert** на странице PR — откат отдельным коммитом, чужой код не страдает |
| Приехал новый модуль в `local/modules/` | Установить/переустановить в админке (*Marketplace → Установленные решения*) — [[recipe-safe-module-deploy]] |

**Никогда не делать `git push --force`** — это единственный способ затереть чужую работу. Обычные
`push` / `pull` / `merge` только добавляют.

## Гигиена репозитория портала
- Файлы, которые правит сам Bitrix на проде (`.top.menu_ext.php` и подобные), внести в
  `.gitignore` — тогда pull перестанет о них спотыкаться и `stash` не понадобится каждый раз.
- Логи и выгрузки (`logs/`, дампы, `*.db`) — в `.gitignore`: они регулярно утаскивают в
  репозиторий вебхуки и персональные данные.
- Секреты в репозиторий не коммитим. Если уже закоммичены — вебхук/пароль **перевыпустить**,
  историю не считать безопасной.
- «Мусорные» ветки на сервере (`my-server-changes` и т. п.) — сохранённые когда-то серверные
  правки; удалять только после проверки прода.
