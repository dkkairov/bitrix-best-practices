# Формат шаблона БП (.bpt): устройство и чтение

**TL;DR:** `.bpt` — это сжатый zlib PHP-`serialize` массива из шести ключей. Файл обратимо
раскладывается в JSON и собирается обратно байт-в-байт, поэтому собирать `.bpt` должен код, а не
человек или модель. Сложны не формат, а недокументированные свойства действий и зашитые в логику
ID портала.

> **Изменено 2026-09-21.** Раньше корпус считался шаблонами роботов облака: корень
> `Bizproc Automation template` мы принимали за признак роботов. Команда уточнила: все файлы
> выгружены из дизайнера БП кнопкой «Экспорт», клиенты — на коробке. Исправлены разделы «Откуда
> берётся», «Шаблоны роботов и шаблоны дизайнера» и «Облако vs коробка».

## Откуда берётся
- Экспорт из дизайнера бизнес-процессов — файл вида `bp-<ID>.bpt`. Документация предлагает готовить
  файл для загрузки через REST именно так
  ([[entity-bizproc-template-rest-methods|REST-методы шаблонов]]).
- Все изученные файлы (16) выгружены из дизайнера БП кнопкой «Экспорт»: шаблоны смарт-процессов
  коробки клиента, в том числе пустой шаблон, созданный для сверки.

## Устройство файла
`.bpt` = `gzcompress(serialize($массив))`. Верхний уровень (проверено на 16 экспортах):

| Ключ | Что внутри |
|------|-----------|
| `VERSION` | версия формата (`2`) |
| `TEMPLATE` | дерево действий; `TEMPLATE[0]` — корень `SequentialWorkflowActivity` |
| `PARAMETERS` | параметры запуска (заполняются при старте процесса) |
| `VARIABLES` | переменные шаблона |
| `CONSTANTS` | константы шаблона |
| `DOCUMENT_FIELDS` | описание полей документа **исходного портала**: коды, названия, типы, варианты списков |

**Типа документа в файле нет** — его задают при загрузке (`DOCUMENT_TYPE` в REST или место импорта
в интерфейсе).

`DOCUMENT_FIELDS` к логике не относится, но занимает почти весь файл: в 10 из 11 изученных
экспортов — 70–96% объёма (72–189 полей).

## Узел-действие
```json
{
  "Type": "SetFieldActivity",
  "Name": "A10001_20002_30003_40004",
  "Activated": "Y",
  "Node": null,
  "Properties": {
    "FieldValue": { "UF_CRM_7_1700000000001": "{=Variable:amount}" },
    "Title": "Изменение документа"
  },
  "Children": []
}
```
- `Type` — класс действия, `Properties` — его настройки. **Набор свойств не документирован** и
  меняется с версиями: например, у «Задачи» (`Task2Activity`) уже есть `FLOW_ID`.
- `Name` — случайный уникальный идентификатор. По нему другие действия берут результаты шага.
- `Activated: "N"` — действие отключено, но осталось в шаблоне.
- Структурные узлы: `SequenceActivity`, `ParallelActivity`, `IfElseActivity` → `IfElseBranchActivity`,
  `WhileActivity`, `EmptyBlockActivity`.

## Выражения
| Запись | Смысл |
|--------|-------|
| `{=Document:TITLE}` | поле документа |
| `{=Variable:имя}`, `{=Constant:имя}`, `{=Template:имя}` | переменная, константа, параметр |
| `{=A50005_60006_70007_80008:InfoUser}` | результат другого действия (по его `Name`) |
| `{=System:Now}` | системные значения |
| `{=Document:TITLE > friendly}`, `… > printable` | модификаторы вывода |
| `=workdateadd({=System:Now},"1d",{=Document:ASSIGNED_BY_ID})` | формула |
| `user_42`, `group_g7`, `group_d3` | пользователь, группа, отдел — ID портала |

## Условия ветвлений
Свойство `IfElseBranchActivity`. В одном файле встречаются разные форматы:

| Свойство | Формат | Пример |
|----------|--------|--------|
| `fieldcondition` | список `[поле, оператор, значение, связка]` | `[ ["UF_CRM_7_1700000000002", "empty", "", "0"] ]` |
| `propertyvariablecondition` | то же, по параметрам и переменным | `[ ["Approved_obligatory", "=", "Y", "0"] ]` |
| `mixedcondition` | объекты | `{"object": "Document", "field": "UF_CRM_…", "operator": "empty", "value": "", "joiner": "0"}` |
| `truecondition` | ветка «иначе» | `"1"` |

Связка `"0"` / `"1"` — по наблюдениям «и» / «или» (эмпирика, сверить в дизайнере).

## Шаблоны роботов и шаблоны дизайнера
- **По `.bpt` их не отличить.** Корень у 15 из 16 экспортов называется `Bizproc Automation template`,
  в том числе у нового пустого шаблона из дизайнера. У одного старого шаблона корень —
  «Последовательный бизнес-процесс». Утилита больше не делит шаблоны на «роботов» и «дизайнер».
- Последовательности внутри `ParallelActivity` называются то «Automation sequence», то
  «Последовательность действий», иногда в одном шаблоне. Похоже на шаблоны, начатые роботами и
  доработанные в дизайнере, — это предположение, не проверено.
- Шаблоны роботов в облаке **через REST недоступны**
  ([[entity-bizproc-template-rest-methods|REST-методы шаблонов]]).

## Как читать и проверять
Утилита [`tools/bpt`](../../../tools/bpt/README.md):

```bash
php tools/bpt/bpt.php analyze bp-154.bpt                    # структура, привязки к порталу, битые ссылки
php tools/bpt/bpt.php compact bp-154.bpt                    # логика деревом, без DOCUMENT_FIELDS
php tools/bpt/bpt.php decode bp-154.bpt -o bp-154.bpt.json  # JSON без потерь
php tools/bpt/bpt.php encode bp-154.bpt.json -o bp-154.bpt --force
```

Проверено: `decode` → `encode` воспроизводит все 16 файлов байт-в-байт.

### Сборка из спецификации и обратный разбор
Собирать `.bpt` вручную не нужно: процесс описывается спецификацией в YAML (формат —
[`tools/bpt/SPEC.md`](../../../tools/bpt/SPEC.md)), а свойства действий берутся из
[[concept-bizproc-activity-catalog|каталога действий]].

```bash
php tools/bpt/bpt.php compile spec.yaml --portal=portal.yaml -o process.bpt  # спецификация → .bpt
php tools/bpt/bpt.php decompile bp-154.bpt                                   # .bpt → спецификация
php tools/bpt/bpt.php render bp-154.bpt                                      # схема Mermaid для ревью
php tools/bpt/bpt.php snapshot bp-154.bpt -o portal.yaml                     # поля и стадии портала
```

Проверено на корпусе из 16 экспортов: разбор в спецификацию и обратная сборка воспроизводят
каждый шаблон по смыслу — и напрямую, и через снимок портала с плейсхолдерами (2026-09-21).

## Почему важно при внедрении
- **Перенос между порталами.** В логике 10 из 11 файлов зашиты ID портала: смарт-процессы, стадии,
  коды полей, сотрудники, группы, адрес портала
  ([[antipattern-bizproc-hardcoded-portal-ids|Зашитые ID портала]]).
- **Ревью и отладка.** Разбор показывает то, чего не видно в дизайнере. В одном шаблоне нашлось
  5 ссылок `{=A…:Comments}` на удалённые шаги согласования. Скорее всего, туда подставлялось пустое
  значение, и комментарии согласующих не доходили до карточки.
- **Генерация агентом.** Модель получает компактную логику, а файл собирает код
  ([[pattern-bizproc-ai-assisted-generation|AI-генерация БП]]).
- **Размер.** Крупный шаблон — 489 узлов, 18 уровней вложенности, 267 КБ после распаковки. Модели
  отдают только `compact` (около 112 КБ для этого шаблона).

## Облако vs коробка
- В изученных экспортах коробки 2026 года — `VERSION` 2, строки в UTF-8. Облачный экспорт и
  экспорты старых коробок пока не разбирали.
- Коробка в `windows-1251`: строки в файле, скорее всего, в этой кодировке. У утилиты есть
  `--charset`, но на реальном файле это не проверялось.
- Действие «PHP-код» (`CodeActivity`) есть только в коробке; при переносе и генерации по умолчанию
  запрещено.
- Загрузка: в облаке — интерфейс или REST из приложения; в коробке — интерфейс или PHP-API модуля
  `bizproc` (сигнатуры сверять с версией).

## Безопасность и конфиденциальность
- Разбирать `.bpt` только через `unserialize(..., ['allowed_classes' => false])`: файл может прийти
  с чужого портала.
- В шаблонах клиента — его логика, ID сотрудников и адрес портала. В git не кладём (`*.bpt` в
  `.gitignore`), в библиотеку — только обезличенные.
