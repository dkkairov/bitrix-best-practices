# Формат шаблона БП (.bpt): устройство и чтение

**TL;DR:** `.bpt` — это сжатый zlib PHP-`serialize` массива из шести ключей. Файл обратимо
раскладывается в JSON и собирается обратно байт-в-байт, поэтому собирать `.bpt` должен код, а не
человек или модель. Сложны не формат, а недокументированные свойства действий и зашитые в логику
ID портала.

> **Изменено 2026-09-21.** Раньше корпус считался шаблонами роботов облака: корень
> `Bizproc Automation template` мы принимали за признак роботов. Команда уточнила: все файлы
> выгружены из дизайнера БП кнопкой «Экспорт», клиенты — на коробке. Исправлены разделы «Откуда
> берётся», «Шаблоны роботов и шаблоны дизайнера» и «Облако vs коробка».

## Откуда берётся
- Экспорт из дизайнера бизнес-процессов — файл `bp-<ID шаблона>.bpt`
  ([урок «Экспорт и импорт»](https://dev.1c-bitrix.ru/learning/course/?COURSE_ID=57&LESSON_ID=3858)).
  Документация предлагает готовить файл для загрузки через REST именно так
  ([[entity-bizproc-template-rest-methods|REST-методы шаблонов]]).
- Все изученные файлы (16) выгружены из дизайнера БП кнопкой «Экспорт»: шаблоны смарт-процессов
  коробки клиента, в том числе пустой шаблон, созданный для сверки.

## Устройство файла
`.bpt` = `gzcompress(serialize($массив))`. Верхний уровень (проверено на 16 экспортах):

| Ключ | Что внутри |
|------|-----------|
| `VERSION` | версия формата (`2`) |
| `TEMPLATE` | дерево действий; `TEMPLATE[0]` — корень `SequentialWorkflowActivity` |
| `PARAMETERS` | параметры запуска (заполняются при старте процесса) |
| `VARIABLES` | переменные шаблона |
| `CONSTANTS` | константы шаблона |
| `DOCUMENT_FIELDS` | описание полей документа **исходного портала**: коды, названия, типы, варианты списков |

**Типа документа в файле нет** — его задают при загрузке (`DOCUMENT_TYPE` в REST или место импорта
в интерфейсе).

`DOCUMENT_FIELDS` к логике не относится, но занимает почти весь файл: в 10 из 11 изученных
экспортов — 70–96% объёма (72–189 полей).

**При импорте `DOCUMENT_FIELDS` применяется к порталу.** Недостающие поля создаются, поля с тем же
кодом могут обновиться, лишние поля приёмника остаются. Импорт **в документ другого типа запрещён**:
на приёмнике заранее создают такой же тип документа, проще всего — импортировать в «пустой». После
импорта проверяют список полей и их упоминания в действиях
([урок «Экспорт и импорт»](https://dev.1c-bitrix.ru/learning/course/?COURSE_ID=57&LESSON_ID=3858)).
Импорт **заменяет текущий шаблон**
([дизайнер](https://dev.1c-bitrix.ru/learning/course/?COURSE_ID=57&LESSON_ID=12409)); для
универсальных списков своя процедура (там же, урок 3858).

> **Изменено 2026-09-22.** Раньше здесь было «импортировать рекомендуют только в документ того же
> типа». Курс формулирует это как запрет — исправлено.

На стенде (коробка, bizproc 26.1075.0, 2026-09-22) импорт создал поле, которого на портале не было;
переименование существующего поля не применил. Пустой раздел импорт пропускает, шаблон работает.
Поэтому [`tools/bpt`](../../../tools/bpt/SPEC.md) по умолчанию пишет его пустым: шаблон, собранный
по снимку одного портала, не оставит на другом чужих полей.

После импорта чужого шаблона (примеры курса,
[урок 5383](https://dev.1c-bitrix.ru/learning/course/?COURSE_ID=57&LESSON_ID=5383)):
- у полей «Привязка к элементам CRM» «Доступная сущность» сбрасывается на «Лид» — выставить вручную;
- роли, заданные в примере пользователем с ID 1, заменить своими;
- в шаблонах списков заменить поля во всех действиях и текстах сообщений.

## Узел-действие
```json
{
  "Type": "SetFieldActivity",
  "Name": "A10001_20002_30003_40004",
  "Activated": "Y",
  "Node": null,
  "Properties": {
    "FieldValue": { "UF_CRM_7_1700000000001": "{=Variable:amount}" },
    "Title": "Изменение документа"
  },
  "Children": []
}
```
- `Type` — класс действия, `Properties` — его настройки. **Набор свойств не документирован** и
  меняется с версиями: например, у «Задачи» (`Task2Activity`) уже есть `FLOW_ID`.
- `Name` — уникальный идентификатор, в дизайнере — «[Ид]» действия: латиница, цифры, `_`; ссылка
  `#<Name>` в адресе дизайнера ведёт к действию. По нему другие действия берут результаты шага
  ([общие моменты](https://dev.1c-bitrix.ru/learning/course/?COURSE_ID=57&LESSON_ID=12321)).
- `Activated: "N"` — действие выключено, но осталось в шаблоне (с bizproc 23.300.0). Всё, что вложено
  в выключенный блок или ветку, тоже не выполняется; импорт свойства выключенных действий не проверяет
  (`validateTemplate`, bizproc 26.1075.0).
- Структурные узлы: `SequenceActivity`, `ParallelActivity`, `IfElseActivity` → `IfElseBranchActivity`,
  `WhileActivity`, `EmptyBlockActivity`.

## Выражения
Полный разбор синтаксиса, функций и модификаторов — [[concept-bizproc-expressions]].

| Запись | Смысл |
|--------|-------|
| `{=Document:TITLE}` | поле документа |
| `{=Variable:имя}`, `{=Constant:имя}`, `{=Template:имя}` | переменная, константа, параметр |
| `{=A50005_60006_70007_80008:InfoUser}` | результат другого действия (по его `Name`) |
| `{=System:Now}`, `NowLocal`, `Date`, `Eol`, `HostUrl` | системные значения; `HostUrl` — адрес сайта, с bizproc 22.200.0 |
| `{=Workflow:ID}`, `{=Template:TargetUser}`, `{=User:ID}` | ID процесса; кто запустил; пользователь текущего хита — после паузы это может быть кто угодно |
| `{=Document:TITLE > friendly}`, `… > printable` | модификаторы вывода; есть ещё `name`, `server`, `local`, `responsible`, `publink`, `shortlink` и преобразования типов |
| `{=Variable:amount_printable}` | печатный вид суффиксом — старая форма модификатора |
| `=workdateadd({=System:Now},"1d",{=Document:ASSIGNED_BY_ID})` | формула; `{{=…}}` вставляет результат в текст |
| `user_42` | пользователь |
| `group_g7` | группа пользователей |
| `group_d3`, `group_dr3` | отдел без подотделов / с подотделами |
| `group_hr2`, `group_hrr2` | узел новой оргструктуры (`humanresources`) без / с подотделами; `group_d…` ядро переводит в узел само |
| `group_sg5_A`, `…_E`, `…_K` | роли в рабочей группе |
| `group_U7`, `group_IU7`, `group_SU7`, `group_UA`, `group_Dextranet` | ещё коды групп из курса, в его написании ([урок 13640](https://dev.1c-bitrix.ru/learning/course/?COURSE_ID=57&LESSON_ID=13640)) |

Токены получателей — ID портала; разбор сверен с `CBPHelper::extractUsersFromExtendedGroup`
(коробка, bizproc 26.1075.0). На стенде `group_d12` в журнале процесса показан как «Бухгалтерия [HR2]».
Курс пишет коды прописными (`group_G7`, `group_DR7`): ядро переводит часть после `group_` в верхний
регистр, так что оба варианта равнозначны; сам префикс `group_` — строчными. Код группы в поле для
одного пользователя даёт её пользователя с наименьшим ID.

Выражение с ошибкой не останавливает процесс — оно выводится как текст
([функции калькулятора](https://dev.1c-bitrix.ru/learning/course/?COURSE_ID=57&LESSON_ID=4912)).
Полный справочник функций и модификаторов — в курсе, уроки
[4912](https://dev.1c-bitrix.ru/learning/course/?COURSE_ID=57&LESSON_ID=4912) и
[12407](https://dev.1c-bitrix.ru/learning/course/?COURSE_ID=57&LESSON_ID=12407).

## Условия ветвлений
Свойство `IfElseBranchActivity`. В одном файле встречаются разные форматы:

| Свойство | Формат | Пример |
|----------|--------|--------|
| `fieldcondition` | список `[поле, оператор, значение, связка]` | `[ ["UF_CRM_7_1700000000002", "empty", "", "0"] ]` |
| `propertyvariablecondition` | то же, по параметрам и переменным | `[ ["Approved_obligatory", "=", "Y", "0"] ]` |
| `mixedcondition` | объекты | `{"object": "Document", "field": "UF_CRM_…", "operator": "empty", "value": "", "joiner": "0"}` |
| `truecondition` | ветка «иначе» | `"1"` |

Связка `"0"` — «и», `"1"` — «или»; «и» связывает сильнее «или»: строки делятся на группы по «или», и
условие истинно, если истинна хотя бы одна группа
([урок «Условие»](https://dev.1c-bitrix.ru/learning/course/?COURSE_ID=57&LESSON_ID=3789); код ядра
`CBPActivityCondition::getJoiner`, `Bizproc\Activity\ConditionGroup`). Ловушка: связка «или» в первой
строке делает всё условие истинным — у шаблонов из дизайнера там всегда `"0"`, а сборщик
`tools/bpt` предупреждает. Ветки «Условия» проверяются по порядку, выполняется первая истинная; если
ни одна не подошла, конструкция пропускается — поэтому нужна ветка «иначе» с `truecondition`.

> **Изменено 2026-09-22.** Смысл связки раньше был наблюдением по корпусу — подтверждён курсом и ядром.

## Шаблоны роботов и шаблоны дизайнера
- **По `.bpt` их не отличить.** Корень у 15 из 16 экспортов называется `Bizproc Automation template`,
  в том числе у нового пустого шаблона из дизайнера. У одного старого шаблона корень —
  «Последовательный бизнес-процесс». Утилита больше не делит шаблоны на «роботов» и «дизайнер».
- Последовательности внутри `ParallelActivity` называются то «Automation sequence», то
  «Последовательность действий», иногда в одном шаблоне. Похоже на шаблоны, начатые роботами и
  доработанные в дизайнере, — это предположение, не проверено.
- Шаблоны роботов в облаке **через REST недоступны**
  ([[entity-bizproc-template-rest-methods|REST-методы шаблонов]]).

## Как читать и проверять
Утилита [`tools/bpt`](../../../tools/bpt/README.md):

```bash
php tools/bpt/bpt.php analyze bp-154.bpt                    # структура, привязки к порталу, битые ссылки
php tools/bpt/bpt.php compact bp-154.bpt                    # логика деревом, без DOCUMENT_FIELDS
php tools/bpt/bpt.php decode bp-154.bpt -o bp-154.bpt.json  # JSON без потерь
php tools/bpt/bpt.php encode bp-154.bpt.json -o bp-154.bpt --force
```

Проверено: `decode` → `encode` воспроизводит все 16 файлов байт-в-байт.

### Сборка из спецификации и обратный разбор
Собирать `.bpt` вручную не нужно: процесс описывается спецификацией в YAML (формат —
[`tools/bpt/SPEC.md`](../../../tools/bpt/SPEC.md)), а свойства действий берутся из
[[concept-bizproc-activity-catalog|каталога действий]].

```bash
php tools/bpt/bpt.php compile spec.yaml --portal=portal.yaml -o process.bpt  # спецификация → .bpt
php tools/bpt/bpt.php decompile bp-154.bpt                                   # .bpt → спецификация
php tools/bpt/bpt.php render bp-154.bpt                                      # схема Mermaid для ревью
php tools/bpt/bpt.php snapshot bp-154.bpt -o portal.yaml                     # поля и стадии портала
```

Проверено на корпусе из 16 экспортов: разбор в спецификацию и обратная сборка воспроизводят
каждый шаблон по смыслу — и напрямую, и через снимок портала с плейсхолдерами (2026-09-21).

## Почему важно при внедрении
- **Перенос между порталами.** В логике 10 из 11 файлов зашиты ID портала: смарт-процессы, стадии,
  коды полей, сотрудники, группы, адрес портала
  ([[antipattern-bizproc-hardcoded-portal-ids|Зашитые ID портала]]).
- **Ревью и отладка.** Разбор показывает то, чего не видно в дизайнере. В одном шаблоне нашлось
  5 ссылок `{=A…:Comments}` на удалённые шаги согласования. Скорее всего, туда подставлялось пустое
  значение, и комментарии согласующих не доходили до карточки.
- **Генерация агентом.** Модель получает компактную логику, а файл собирает код
  ([[pattern-bizproc-ai-assisted-generation|AI-генерация БП]]).
- **Размер.** Крупный шаблон — 489 узлов, 18 уровней вложенности, 267 КБ после распаковки. Модели
  отдают только `compact` (около 112 КБ для этого шаблона).

## Облако vs коробка
- В изученных экспортах коробки 2026 года — `VERSION` 2, строки в UTF-8. Облачный экспорт и
  экспорты старых коробок пока не разбирали.
- Коробка в `windows-1251`: строки в файле, скорее всего, в этой кодировке. У утилиты есть
  `--charset`, но на реальном файле это не проверялось.
- Действие «PHP-код» (`CodeActivity`) есть только в коробке; при переносе и генерации по умолчанию
  запрещено.
- Загрузка: в облаке — интерфейс или REST из приложения. В коробке кнопка «Импорт» в дизайнере,
  REST `bizproc.workflow.template.add/update` и PHP сходятся в одном методе —
  `CBPWorkflowTemplateLoader::ImportTemplate($id, $documentType, $autoExecute, $name, $description, $datum)`
  (bizproc 26.1075.0, проверено на стенде 2026-09-22). Импорт проверяет свойства каждого действия
  (`ValidateProperties`) от имени импортирующего: например, без отправителя «Уведомления
  пользователя» или сообщения в чат, без постановщика задачи шаблон не примется, а не администратор
  может указать отправителем уведомления только себя. Для переноса между установками нужны права
  администратора
  ([урок «Экспорт и импорт»](https://dev.1c-bitrix.ru/learning/course/?COURSE_ID=57&LESSON_ID=3858)).

## Безопасность и конфиденциальность
- Разбирать `.bpt` только через `unserialize(..., ['allowed_classes' => false])`: файл может прийти
  с чужого портала.
- В шаблонах клиента — его логика, ID сотрудников и адрес портала. В git не кладём (`*.bpt` в
  `.gitignore`), в библиотеку — только обезличенные.
