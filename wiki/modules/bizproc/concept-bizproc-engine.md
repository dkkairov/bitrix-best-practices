# Устройство движка БП

**TL;DR:** шаблон, собранный в дизайнере, при запуске **копируется** в экземпляр, и дальше процесс
идёт по копии. Кубик исполнения — активити; робот — это тот же класс активити с другим типом.
Источники — раздел «Модуль Бизнес-процессы» «Книги разработчика»
([О модуле](https://bx24devbook.website.yandexcloud.net/Modul_Biznes_processy/O_module.html)),
официальный курс 57 ([глоссарий](https://dev.1c-bitrix.ru/learning/course/?COURSE_ID=57&LESSON_ID=26972),
[настройки модуля](https://dev.1c-bitrix.ru/learning/course/?COURSE_ID=57&LESSON_ID=4678),
[шаблон](https://dev.1c-bitrix.ru/learning/course/?COURSE_ID=57&LESSON_ID=3465) и
[экземпляр](https://dev.1c-bitrix.ru/learning/course/?COURSE_ID=57&LESSON_ID=2130) для разработчика) и
код ядра на стенде.

> **Сверено с курсом 57 и ядром 2026-09-22.** Добавлены официальные термины, типы процессов, лимиты
> модуля и что бывает при их превышении, автозапуск. Порядок поиска действий и «первое совпадение»
> подтверждены кодом ядра; спор о базовом классе задания снят (раздел «По характеру выполнения»).

## Терминология

| Термин | Что это |
|---|---|
| **Бизнес-процесс** | алгоритм достижения цели (понятие) |
| **Шаблон БП** | схема процесса в дизайнере **над определённым типом документа**; в базе — массив действий `Type` / `Name` / `Properties` / `Children` |
| **Документ** | объект, над которым идёт процесс: элемент инфоблока или списка, файл общего диска, элемент CRM, процесс ленты новостей; бывает «виртуальным» |
| **Действие / активити / шаг** | атомарная операция, «визуальный кубик»; сам процесс — корневое составное действие |
| **Экземпляр (инстанс)** | копия шаблона в момент запуска |
| **Параметры** | вводит тот, кто запускает; процесс их не меняет |
| **Переменные** | меняются по ходу выполнения, стираются после завершения процесса |
| **Константы шаблона** | задаются в шаблоне, во время выполнения только читаются |
| **Глобальные переменные и константы** | общие для шаблонов с учётом видимости — [[entity-bizproc-globals-manager]] |
| **Задание** | шаг, который ждёт человека: утвердить, ознакомиться, ввести данные |
| **Журнал / протокол** | журнал — отладочная запись шагов процесса; протокол — история заданий |

Термины — по глоссарию курса и книге. Нужное после завершения процесса сохраняют в поле документа:
переменные исчезают вместе с процессом.

## Где работают бизнес-процессы
- CRM: лиды, контакты, компании, сделки, предложения, счета (новые — с crm 21.1300.0), смарт-процессы
  с включённой опцией дизайнера БП.
- Универсальные списки и процессы ленты новостей; файлы **общего** диска (не «Мой диск»).
- Коробка: элементы инфоблоков (через административный раздел) и устаревшая библиотека документов.
- В редакциях «Управления сайтом» Старт, Стандарт и Малый бизнес модуля нет; «Дизайнер» — в старших
  редакциях.

([Общая информация](https://dev.1c-bitrix.ru/learning/course/?COURSE_ID=57&LESSON_ID=1708),
[создать шаблон](https://dev.1c-bitrix.ru/learning/course/?COURSE_ID=57&LESSON_ID=26610))

## Два типа процессов
- **Последовательный** — цепочка шагов от начала до конца.
- **Со статусами** — у документа есть состояния, переходы по командам или времени и свои права в каждом
  статусе. У статуса до четырёх подпроцессов: вход, выход, команда, выполнение через время. Если смена
  статуса не задана, процесс завершается. Подробно — [[concept-bizproc-state-machine]].

Курс предупреждает: неудачный выбор типа сильно усложняет шаблон
([выбор типа](https://dev.1c-bitrix.ru/learning/course/?COURSE_ID=57&LESSON_ID=3468)). Утилита
[`tools/bpt`](../../../tools/bpt/README.md) собирает только последовательные процессы.

## Принцип изоляции

Шаблон **копируется в экземпляр** при запуске. Отсюда два следствия, о которых регулярно
приходится напоминать заказчику:

- правка шаблона **не влияет** на уже запущенные процессы — они доживут по старой логике (так и в
  курсе; книга называет остановку запущенных процессов при изменении шаблона неправильным выходом);
- «исправить зависший процесс» правкой шаблона нельзя: его останавливают и запускают заново
  (практика команды).

Шаблон, у которого есть незавершённые процессы, удалить нельзя
([урок 7290](https://dev.1c-bitrix.ru/learning/course/?COURSE_ID=57&LESSON_ID=7290)). Ожидающий процесс
сохраняется в базе и выгружается из памяти; по сроку или событию восстанавливается. Одновременно
работает одна копия экземпляра, иначе «заблокирован другим процессом»
([урок 2130](https://dev.1c-bitrix.ru/learning/course/?COURSE_ID=57&LESSON_ID=2130)).

БП запускается только на объектах, которые поддерживают эту механику: задачи — частично, старые
счета и события календаря — нет (книга).

## Лимиты модуля

| Настройка (коробка) | Облако | Что будет при превышении (код ядра, bizproc 26.1075.0) |
|---|---|---|
| «Максимальное количество одновременно запущенных над документом процессов» | 2 | новый процесс **не стартует**: ошибка «не более N процессов» (`CBPRuntime::createWorkflow`) |
| «Минимальное время ожидания для действий» | 5 минут | меньший срок паузы или задания поднимается до минимума (`CBPSchedulerService::calculateExpirationTime`) |
| «Максимальное количество итераций цикла в рамках одного запуска» (с 25.100.0) | 1000 | ошибка в журнал и выход из цикла; на один цикл, кроме того, жёсткий предел 1000 итераций |
| «Время хранения лога выполнения» | журнал пишется 7 дней после включения в шаблоне (с 01.08.2024) | старые записи удаляются; по умолчанию 90 дней |

Курс советует на коробке начинать с облачных значений
([урок 4678](https://dev.1c-bitrix.ru/learning/course/?COURSE_ID=57&LESSON_ID=4678)). Параметр
`limit_simultaneous_processes` = 0 — без ограничения.

## Автозапуск
- Шаблон запускается «при создании» и/или «при изменении» документа; оба флажка сняты — только вручную
  ([параметры шаблона](https://dev.1c-bitrix.ru/learning/course/?COURSE_ID=57&LESSON_ID=3816)).
- У инфоблока автозапуск срабатывает только на изменения из административного раздела, а процесс,
  который может вызвать сам себя, курс запрещает ставить на «при изменении» — зациклится
  ([урок 3122](https://dev.1c-bitrix.ru/learning/course/?COURSE_ID=57&LESSON_ID=3122)).
- **CRM:** изменения, которые делает сам процесс, по умолчанию автозапуск не вызывают — нужна опция
  CRM `start_bp_within_bp` = `Y` (код ядра, crm 26.800.0); на стенде так и вышло (2026-09-22). Правки
  пользователя запускают новый экземпляр на каждое изменение — [[entity-robots-triggers]].

## Три типа активити

Тип задаётся в `.description.php` ([[entity-bizproc-activity-description]]):

| `TYPE` | Что это | Базовый класс |
|---|---|---|
| `activity` | действие в шаблоне БП | `CBPActivity` (или `BaseActivity`) |
| `condition` | условие для блоков «Условие» и «Цикл» | `CBPActivityCondition` |
| `robot_activity` | **робот** (CRM и другие) | тот же `CBPActivity` + `ROBOT_SETTINGS` |

Один класс может зарегистрироваться сразу как действие и как робот: `TYPE = ['activity',
'robot_activity']`. То есть роботы — не отдельная технология, а подвид активити; выбор между ними
на уровне внедрения — [[pattern-robots-vs-bizproc-decision]]. В bizproc 26.x описание всё чаще
собирают классом `Bitrix\Bizproc\Activity\ActivityDescription`, появились типы для нового узлового
конструктора (код ядра).

## По характеру выполнения

| Тип | Когда | Что требуется |
|---|---|---|
| **Немедленное** (по умолчанию) | сделать и продолжить | ничего особого |
| **Событийное** | ждать внешнее событие | `IBPEventActivity` + `IBPActivityExternalEventListener` |
| **Задание** | ждать решения человека | те же интерфейсы + методы формы задания; базовый класс — см. ниже |

Книга называет базовым классом задания `CBPCompositeActivity`. В ядре (bizproc 26.1075.0) штатны оба:
`CBPReviewActivity` («Ознакомление», без веток) наследует `CBPActivity`, а `CBPApproveActivity` и
`CBPRequestInformationActivity` (с ветками) — `CBPCompositeActivity`. Задание без веток —
`CBPActivity`, с ветками «да/нет» — `CBPCompositeActivity`. Своё задание целиком —
[[recipe-bizproc-custom-task-activity]].

Структурно активити делятся на **простые** (выполняются сами) и **композитные** (содержат
дочерние, наследуются от `CBPCompositeActivity`).

## Где живут свои активити

Порядок поиска (книга; подтверждено кодом `Bitrix\Bizproc\Runtime\ActivitySearcher\Searcher`):

1. `/local/activities/`
2. `/local/activities/custom/`
3. `/bitrix/activities/custom/`
4. `/bitrix/activities/bitrix/`
5. `/bitrix/modules/bizproc/activities/`

Берётся **первое совпадение**: одноимённый каталог выше по списку перекрывает штатное действие во всех
шаблонах. Имя своего каталога не должно совпадать со штатным — в курсе примеры `logactivity` и
`task2activity` как раз совпадают со штатными. Штатные действия на стенде лежат в
`/bitrix/activities/bitrix/` (219 каталогов), пятого каталога там нет. Курс кладёт свои действия в
`/bitrix/activities/custom/` — это устаревший совет; своё кладём в `/local/activities/custom/`.
Каталога своего модуля в списке нет: модуль при установке копирует действие в один из этих
каталогов (обычно `/local/activities/custom/<имя>/`) и убирает его при удалении. Имя каталога = имя
класса без префикса `CBP` в нижнем регистре: `CBPHelloWorldActivity` → `helloworldactivity/`.

Каноническая структура каталога:

```
<name>/
├── .description.php            — $arActivityDescription
├── <name>.php                  — класс активити
├── properties_dialog.php       — форма настроек (для activity); при getPropertiesDialogMap() — только для своей отрисовки
├── robot_properties_dialog.php — форма настроек (для robot_activity)
└── lang/<lang>/
```

## Подключение модуля

В отличие от `main` и `intranet` (последний гарантирован в публичной части), `bizproc` может быть не
установлен или не подключён — книга требует явной проверки:

```php
if (\Bitrix\Main\Loader::includeModule('bizproc')) { /* … */ }
```

Соседний модуль `bizprocdesigner` — только визуальный редактор шаблонов.

## Почему важно при внедрении

Своё активити — уровень 2 [[concept-change-invasiveness-hierarchy|иерархии]]: легитимное
расширение, которое переживает обновления продукта. Почти любая просьба «пусть процесс делает
что-то нестандартное» решается своим действием, а не правкой ядра, не внешним сервисом и не
действием «PHP код» ([[antipattern-bizproc-php-code-activity]]). В облаке тот же приём — действие
или робот приложения по REST ([[entity-bizproc-template-rest-methods]]).
