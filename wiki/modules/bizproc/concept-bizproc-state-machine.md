# БП со статусами: устройство и когда выбирать

**TL;DR:** процесс со статусами описывает документ как набор состояний. В каждом статусе — свои права
и свои подпроцессы: вход, выход, команды пользователей и выполнение через время. Переход — действием
«Установить статус». Если перехода нет, процесс завершается. Выбирают его, когда у документа есть
жизненный цикл с переходами «туда-обратно» и правами на каждом шаге; для CRM это чаще роботы на
стадиях. Утилита `tools/bpt` такие процессы пока не собирает.

> **Черновик.** Устройство сверено с двумя примерами курса — `statuses_simple.bpt` (урок 3861) и
> `crm_bp.bpt` (5384),
> [файлы](../../../raw/sources/2026-09-22-course57-bizproc-files/README.md), — и с кодом ядра
> (bizproc 26.1075.0). На стенде 2026-09-22 проверены переходы «Установить статус» и завершение
> процесса. Команды и выполнение через время описаны по курсу и классам ядра: в примерах курса их нет.

## Что это и как работает
Курс: [бизнес-процесс со статусами](https://dev.1c-bitrix.ru/learning/course/?COURSE_ID=57&LESSON_ID=3467),
[создание шаблона](https://dev.1c-bitrix.ru/learning/course/?COURSE_ID=57&LESSON_ID=3860),
[установить статус](https://dev.1c-bitrix.ru/learning/course/?COURSE_ID=57&LESSON_ID=3859),
[команда](https://dev.1c-bitrix.ru/learning/course/?COURSE_ID=57&LESSON_ID=3788).

| Элемент | В дизайнере | Класс в ядре |
|---|---|---|
| Процесс | «Бизнес-процесс со статусами» | `StateMachineWorkflowActivity` — корень шаблона |
| Статус | прямоугольник статуса | `StateActivity`; начальный задаёт свойство корня `InitialStateName`, а не место на схеме |
| Вход в статус | «Обработчик входа в данный статус» | `StateInitializationActivity` |
| Выход из статуса | «Обработчик выхода из данного статуса» | `StateFinalizationActivity` |
| Команда | «Команду» — кнопка для пользователей в статусе | `EventDrivenActivity` («Оболочка события») с `HandleExternalEventActivity` («Команда») внутри |
| Выполнение через время | «Выполнение через заданное время» | та же оболочка события с паузой (`DelayActivity`) — вывод по названиям классов |
| Переход | «Установить статус»: «Перевести в статус», «Прервать выполнение текущего статуса» | `SetStateActivity`: `TargetStateName`, `CancelCurrentState` |

**Порядок в статусе:** обработчик входа → ожидание команды или таймера → «Установить статус» →
обработчик выхода → вход в следующий статус. Настраивать все четыре подпроцесса не обязательно.
Если обработчик входа сам переводит статус, команды и таймер пропускаются.

**Как работает «Установить статус»** (стенд, bizproc 26.1075.0):
- без «Прервать выполнение текущего статуса» переход откладывается до конца обработчика: следующие
  действия выполняются, а из нескольких «Установить статус» подряд побеждает последний;
- с этим флагом переход сразу, остаток обработчика не выполняется, в журнале — «Выполнение текущего
  статуса прервано». Так пример 5384 возвращает документ в тот же или предыдущий статус.

- С bizproc 21.400.0 статусы можно переставлять и менять начальный.
- «Выполнить команду могут» — пользователи и группы из раздела «Пользователи» формы, не из «Категорий
  пользователей»; результат команды — «Пользователь, отправивший команду». Поле «После выполнения
  команды установить статус документа» дизайнер превращает в «Установить статус».
- **Права в статусе** действуют, пока процесс в нём: для списков — 8 видов прав, для инфоблоков — 2,
  для CRM их нет. При переходе права, выставленные «Установкой прав» в текущем статусе,
  перезаписываются. Названия на стенде: у списков это задачи прав инфоблока — «Нет доступа»,
  «Добавление», «Чтение», «Просмотр в панели», «Добавление в панели», «Изменение с ограничениями»,
  «Изменение», «Полный доступ»; у инфоблока с простыми правами — «Чтение» и «Запись». При входе в
  статус выданные права пишутся в журнал.
- **Процесс без перехода завершается**, а не зависает: если в статусе нет «Установить статус», команд
  и таймера, процесс получает итог «Завершён», а у документа остаётся название последнего статуса
  (стенд). «Прерывание процесса» в конечном статусе, как в примере 3861, не нужно: итог станет
  «Прерван», а текст статуса — «Выполнение прервано», если свой не задан (код ядра).

## Когда выбирать
- **Да:** документ проходит состояния с возвратами («на доработку» → «на согласовании» → «утверждён»),
  в каждом состоянии разные права и разные команды пользователей; пример курса — счёт клиенту в CRM на
  11 статусов ([урок 5384](https://dev.1c-bitrix.ru/learning/course/?COURSE_ID=57&LESSON_ID=5384)).
  В файле примера команд нет: каждый статус — обработчик входа с заданиями и «Установить статус»,
  стадия сделки меняется «Изменением документа».
- **Нет:** линейный маршрут — хватит последовательного процесса с циклом доработки; в CRM состояния —
  это стадии воронки, и их обслуживают роботы
  ([[pattern-robots-vs-bizproc-decision|роботы или БП]]).
- Курс предупреждает: неудачный выбор типа сильно усложняет шаблон
  ([урок 3468](https://dev.1c-bitrix.ru/learning/course/?COURSE_ID=57&LESSON_ID=3468)).

## Почему важно при внедрении
- В файле шаблона корень — `StateMachineWorkflowActivity`, а не `SequentialWorkflowActivity`;
  [`tools/bpt`](../../../tools/bpt/SPEC.md) такие шаблоны разбирает (`analyze`, `compact`, `render`),
  а собирать из спецификации не умеет.
- Права по статусам — единственный штатный способ менять доступ к документу по ходу процесса в списках
  и инфоблоках; в CRM его нет.
- Команды — это ожидание людей без срока: таймаут даёт только «Выполнение через заданное время» в том
  же статусе.

## Облако vs коробка
Процессы со статусами есть в обеих редакциях там, где доступен дизайнер БП. Права статуса для
инфоблоков — только коробка (инфоблоки в облаке недоступны).
