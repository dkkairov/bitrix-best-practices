# AI-генерация бизнес-процессов: агент проектирует, код собирает

> **Черновик:** оценка на 10 задачах пройдена (шаг 8: 8 из 10, ровно порог 80%, 2026-09-23, коробка);
> облако и реальные ТЗ команды — нет.
>
> **Обновлено 2026-09-22 (курс 57 и ядро).** Каталог знает смысл значений, варианты и поведение
> действий: что будет по истечении срока задания, типы делегирования, виды сообщений, полные списки
> результатов. Сборщик по проверке импорта на стенде требует постановщика задачи и отправителя
> сообщения в чат, предупреждает о значениях вне вариантов дизайнера и о связке «или» в первой строке
> условия. Агенту это видно в `bpt.php catalog <алиас>`.
>
> **Сделано (2026-09-21):** шаги 2–3 — [[concept-bizproc-activity-catalog|каталог
> действий]] (25 типов) и инструменты в `tools/bpt`: сборка из спецификации, обратный разбор,
> проверки, снимок портала и схема. Разбор и сборка воспроизводят все 16 шаблонов корпуса.
> Шаг 6 — навык Claude Code (ниже). Дальше — живой снимок и загрузка через REST, хуки.
>
> **Уточнено 2026-09-21:** корпус — экспорты из дизайнера БП с коробки клиента, а не роботы облака.
> Все клиенты команды на коробке, поэтому тестовый портал для пилота (шаг 5) — коробка в Docker
> ([[recipe-box-test-stand-docker|рецепт стенда]], развёрнут 2026-09-21);
> облачный NFR-портал — только для облачных вопросов.
>
> **Пилот на коробке пройден (2026-09-22, стенд, bizproc 26.1075.0).** Путь по навыку: снимок с
> живого портала → спецификация → сборка → импорт → автозапуск при создании → согласование
> бухгалтерией (отдел) → обе ветки. Утвердили — стадия «Клиент» и запись в истории от согласующего;
> отклонили — «Доработка» и уведомление руководителю из константы. Импорт в дизайнере, REST и PHP —
> один метод `CBPWorkflowTemplateLoader::ImportTemplate`, он проверяет свойства действий. Пилот
> нашёл три ошибки инструментов, исправлены в `tools/bpt`: не было обязательного отправителя
> уведомления, не проверялись значения `ApproveType`, в файл попадали `DOCUMENT_FIELDS` — а импорт
> создаёт по ним поля на портале. Поведение движка — в
> [[concept-bizproc-activity-catalog|каталоге действий]]. Облако пилотом не проверялось, поэтому
> статус — черновик.

## Проблема и контекст
Цель — чтобы ИИ-агент (Claude Code) сам проектировал и настраивал бизнес-процессы по ТЗ, опираясь
на MCP документации Bitrix24, вики и библиотеку готовых шаблонов. Наивный подход «пусть модель
напишет `.bpt`» не работает:
- формат внутренний и недокументированный ([[concept-bizproc-bpt-format|формат .bpt]]);
- в шаблонах зашиты ID конкретного портала
  ([[antipattern-bizproc-hardcoded-portal-ids|Зашитые ID портала]]);
- проверка синтаксиса не ловит смысловые ошибки: не та ветка, не тот согласующий;
- загрузить можно не всё — шаблоны роботов через REST недоступны
  ([[entity-bizproc-template-rest-methods|REST-методы шаблонов]]).

## Решение
Разделить работу: **модель проектирует логику, код собирает и проверяет, человек утверждает,
тестовый портал подтверждает.**

```text
ТЗ → спецификация (YAML) → ✅ ревью → сборка .bpt → проверка → тестовый портал
   → прогон сценариев → ✅ приёмка → боевой портал
```

- Модель пишет короткую спецификацию с понятными названиями, а не `.bpt`.
- Код генерирует имена действий и связывает ссылки между шагами, подставляет ID из снимка портала,
  добавляет свойства по умолчанию из каталога, собирает `.bpt` и прогоняет проверки.
- Готовые шаблоны — источник каталога действий и эталонных примеров, а не заготовки для
  копирования целиком.

## Когда применять
- Повторяющиеся процессы (согласования, заявки, договоры) на смарт-процессах и списках.
- Есть тестовый портал и владелец процесса, который утверждает схему.
- Шаблоны из дизайнера — их можно загрузить через REST из приложения.

## Когда НЕ применять
- Простая автоматизация по стадиям — роботами руками быстрее
  ([[pattern-robots-vs-bizproc-decision|Роботы vs БП]]).
- Роботы на стадиях в облаке: загрузка только вручную, агент выдаёт спецификацию и инструкцию.
- Нет тестового портала — сгенерированный процесс негде проверить.
- Данные клиента нельзя передавать во внешнюю LLM (NDA) — сначала обезличить или отказаться.

## Как реализовать
1. **Корпус.** Собрать 30–50 экспортов разных видов и обезличить их. Прогнать
   `php tools/bpt/bpt.php analyze` — получится перечень типов действий и их свойств.
2. **Каталог действий.** Для каждого типа — свойства, значения по умолчанию, эталонный пример.
   Модель использует **только** действия из каталога. Сделано:
   [[concept-bizproc-activity-catalog|каталог действий]], формат спецификации — в
   [`tools/bpt/SPEC.md`](../../../tools/bpt/SPEC.md).
3. **Инструменты — это код, не модель:** разбор и сборка `.bpt`
   ([`tools/bpt`](../../../tools/bpt/README.md)), компилятор спецификации, проверки (ссылки,
   объявления, запрещённые действия, «сырые» ID), схема процесса в Mermaid для ревью.
4. **Снимок портала через REST:** смарт-процессы ([`crm.type.list`](https://apidocs.bitrix24.ru/api-reference/crm/universal/user-defined-object-types/crm-type-list.html)), стадии, поля, пользователи и
   структура — чтобы подставлять ID по названиям.
5. **Тестовый портал и своё приложение** со scope `bizproc` и `crm`: загрузка
   ([`bizproc.workflow.template.add`](https://apidocs.bitrix24.ru/api-reference/bizproc/template/bizproc-workflow-template-add.html)), запуск
   ([`bizproc.workflow.start`](https://apidocs.bitrix24.ru/api-reference/bizproc/bizproc-workflow-start.html)), задания
   ([`bizproc.task.list`](https://apidocs.bitrix24.ru/api-reference/bizproc/bizproc-task/bizproc-task-list.html) /
   [`bizproc.task.complete`](https://apidocs.bitrix24.ru/api-reference/bizproc/bizproc-task/bizproc-task-complete.html)) — см.
   [[entity-bizproc-template-rest-methods|REST-методы шаблонов]].
6. **Навык Claude Code** — сделано:
   [`building-bizproc-templates`](../../../.claude/skills/building-bizproc-templates/SKILL.md).
   Задаёт набор файлов результата (спецификация, снимок, `.bpt`, схема, README), порядок работы
   (снимок → спецификация → сборка `--strict` → схема → README) и таблицу решений, которые агент
   принимает явно: автозапуск, повторное согласование, группа или отдел, срок задания, что такое
   «история». Отдельный агент-ревьюер — для процессов длиннее 10 шагов; короткие агент проверяет
   сам по той же таблице.
   *Проверка (2026-09-21, одна задача — согласование суммы в смарт-процессе, синтетический снимок):*
   без навыка агент потратил ~316 тыс. токенов, 87 вызовов и ~18 мин, затем ревьюер ещё ~152 тыс.
   токенов. Время ушло на поиск значений свойств в интернете и свои скрипты перепроверки утилиты.
   С навыком — ~174 тыс. токенов, 39 вызовов, ~9 мин. Все замечания ревьюера из первого прогона
   учтены без ревьюера. Одна задача — не статистика: оценку по шагу 8 это не заменяет.
7. **Хуки:** проверка после каждой записи спецификации, запрет обращений к боевому порталу.
8. **Оценка качества:** 10–15 эталонных задач. Метрики: проходит проверку → загружается → сценарий
   отрабатывает → ревьюер согласен. Реализовано в [tools/bpt-eval](../../../tools/bpt-eval/README.md):
   задачи — данные (ТЗ агенту, сценарии, эталон), прогонщик на стенде отвечает на задания от имени
   ролей и сверяет стадию, поля, историю, уведомления, задачи и наблюдателей.

   *Результат (2026-09-23, коробка 26.x, исполнитель — Sonnet 5, по одному прогону на задачу):*
   **8 задач из 10** прошли целиком — ровно порог 80%. Пилот (T01, T04, T10) — 3 из 3; основной
   прогон (T02, T03, T05–T09) — 5 из 7. Ни одна задача не упала на стенде: все решения собрались,
   импортировались и отработали сценарии. Оба провала — не поднятый в README обязательный вопрос
   к заказчику, и оба одного рода: **кого ещё уведомить** (T03 — сообщать ли об отказе тем, кто уже
   согласовал) и **что если исполнитель не может или отказывается** (T07 — у «Запроса информации»
   отказа нет вовсе, процесс ждёт бессрочно). Обоих пунктов нет в таблице решений навыка — это и
   есть найденное слабое место; правка навыка — отдельным шагом с проверкой до и после.

   *Правка навыка по этим двум местам и её проверка (2026-09-23):* в таблицу решений добавлены две
   строки — «кого ещё уведомить» (инициатор, уже согласовавшие, руководитель, ответственный) и
   «исполнитель не может или отказывается» (у `request_info` ветки отказа нет вовсе: не ответят —
   процесс ждёт бессрочно; нужен отказ — `request_info_optional`, нужен предел — срок). Форма правки
   выбрана по природе провала: не абзац-напоминание, а строки в таблицу, которую агент и так
   заполняет — всё, что в ней было, агенты поднимали исправно, пропускали ровно то, чего не было.
   Повторный прогон тех же двух задач свежими агентами: **обе пройдены** (T03 — 2/2 сценария и 4/4
   вопроса, было 3/4; T07 — 1/1 и 3/3, было 2/3). Долю по всем десяти задачам после правки не
   перемеряли.

   *Полный перемер после правки (2026-09-24, все десять задач заново, свежие агенты):* снова
   **8 из 10**, но упали другие: T03 после правки прошла, зато провалилась T02 (не поднят вопрос,
   что делать при незаполненной сумме), а T07 провалилась снова. Стенд опять 10/10. Главный вывод
   не про навык, а про измерение: **один прогон на задачу даёт разброс, сравнимый с измеряемым
   эффектом** — две задачи поменяли исход без единой правки в них самих. Доля 8/10 устойчива,
   состав провалов — нет.

   *Вторая итерация (2026-09-24):* строка про отказ разведена на две — «отказывается» (есть ли у
   выбранного действия отказ вообще) и «не отвечает» (срок); добавлена строка «поле, от которого
   зависит ветка или роль, не заполнено». Проверка: T02 пройдена (2/2 сценария, 3/4 чек-листа,
   непройденный пункт необязательный) — защитные ветки на пустую сумму и непривязанный проект агент
   построил сам. T07 прогнали дважды независимыми агентами: 3/3 и 1/3. В провальном прогоне отказ
   упомянут как факт схемы («ветки отказа у процесса нет»), но в вопросы заказчику не вынесен, а
   обязательность полей решена молча в спецификации. То есть **природа провала сменилась**: раньше
   пункта не было в таблице решений, теперь он есть, но ничто не заставляет агента пройти таблицу
   по строкам — что вспомнилось, то и попало в README.

   Побочные выводы прогона: роли из карточки «Проекта» агенты находят сами (4 задачи из 7 —
   через «Получить информацию об элементе CRM»); недоступное требование агент распознаёт и
   предлагает замену (T10 — письма клиенту на e-mail этим набором действий нет); эталоны и
   проверки должны лежать вне досягаемости агента — три агента подряд сами сообщили, что видели
   их в репозитории (одну задачу пришлось перегонять).
9. **Пилот:** один смарт-процесс, только шаблоны дизайнера.

Пример спецификации (формат — [`tools/bpt/SPEC.md`](../../../tools/bpt/SPEC.md), полный пример —
`tools/bpt/examples/invoice-approval.bizproc.yaml`):
```yaml
bizproc: 1
name: Согласование счёта
steps:
  - approve:
      id: fin
      Users: ["{{group:Бухгалтерия}}"]              # → ID группы из снимка портала
      Name: "Согласуйте счёт {=Document:TITLE}"
      on_yes:
        - change_stage: {TargetStatus: "{{stage:Общая/Клиент}}"}
      on_no:
        - notify:
            MessageSite: "Отклонено: {=@fin:Comments}"   # ссылка на результат шага
            # отправитель обязателен при импорте; у задания без срока в ветке «нет» он всегда есть,
            # со сроком — MessageType "4" (от системы), как в полном примере
            MessageUserFrom: ["{=@fin:LastApprover}"]
            MessageUserTo: ["{{user:Иванов Иван}}"]
```

| Механизм Claude Code | Роль |
|----------------------|------|
| `CLAUDE.md` и вики | правила, паттерны, антипаттерны; каждая пойманная ошибка → правило проверки или страница |
| Навык (skill) | порядок работы, каталог, обезличенные примеры; подгружается по требованию |
| Скрипты | сборка и разбор, проверки, схема |
| MCP документации Bitrix24 | сверка REST-методов |
| Доступ к порталу (своё приложение) | снимок, загрузка, тесты |
| Агент-ревьюер | независимая сверка логики с ТЗ |
| Хуки | автоматические проверки и запреты |

## Риски
| Риск | Что делать |
|------|-----------|
| Модель придумывает свойства действий | использовать только каталог и проверять по нему |
| Зашитые ID портала | снимок портала, подстановка по названиям, запрет «сырых» ID |
| Смысловые ошибки, циклы, ожидания без таймаута | схема на ревью, сценарные тесты, предупреждения `analyze` |
| Тесты шлют уведомления и ставят задачи живым людям | только тестовый портал; хук запрещает боевые адреса |
| Bitrix24 меняется (новые свойства, например `FLOW_ID` у задачи) | версия в каталоге, повторные тесты на эталонах, дата `verified` |
| Конфиденциальность клиентских шаблонов | обезличивание, NDA, `*.bpt` вне git |
| Большие шаблоны перегружают контекст модели | модели отдавать только `compact` |

## Последствия
- **Плюсы:** знание хранится в файлах — правится одной строкой, версионируется и проверяется; ошибки
  ловятся до портала; процессы стандартизируются.
- **Минусы/компромиссы:** нужны тестовый портал, своё приложение и поддержка каталога при обновлениях
  Bitrix24. Роботов в облаке всё равно ставят вручную. Финальная ответственность — на человеке.

## Альтернативы
- **Дообучить модель — нет.** Для моделей, на которых работает Claude Code, пользовательского
  дообучения нет. Публично доступно только дообучение Claude 3 Haiku в Amazon Bedrock (регион US West,
  до 10 000 примеров, контекст до 32 тыс. токенов). Это модель 2024 года, в API Anthropic её вывод из
  эксплуатации назначен на 19.04.2026. Но даже при наличии дообучения знание внутри модели устаревало
  бы с каждым обновлением Bitrix24 и не проверялось бы по источнику. Источники (на 2026-09):
  [Anthropic](https://www.anthropic.com/news/fine-tune-claude-3-haiku),
  [AWS](https://aws.amazon.com/blogs/aws/fine-tuning-for-anthropics-claude-3-haiku-model-in-amazon-bedrock-is-now-generally-available/).
- **Модель пишет `.bpt` или JSON напрямую** — хрупко: случайные имена, ссылки между шагами, четыре
  формата условий.
- **Вручную в дизайнере** — базовый вариант; паттерн окупается на повторяющихся процессах.
