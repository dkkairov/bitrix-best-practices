# Роли процесса — из карточки проекта, а не из шаблона

## В чём суть

Кто согласует заявку, зависит от проекта, а не от шаблона. Поэтому исполнителей не выбирают в
действии процесса и не выносят в константы: в смарт-процессе «Проекты» заводят поля-сотрудники
(«Руководитель проекта», «Сметчик», «Бухгалтер проекта»), рабочий документ привязывают к проекту
полем-привязкой, а процесс читает роль из карточки проекта на ходу — действием **«Получить
информацию об элементе CRM»** (`CrmGetDynamicInfoActivity`, алиас `get_smart_item` в
[tools/bpt](../../../tools/bpt/SPEC.md)).

Один шаблон обслуживает все проекты. Смена руководителя — правка карточки проекта, а не шаблона:
процессы, запущенные после правки, пойдут к новому человеку.

## Когда применять

- Исполнитель зависит от объекта (проект, филиал, направление), а не от типа документа.
- Ролей несколько и они меняются: перевод сотрудника не должен требовать выгрузки и правки `.bpt`.
- Один и тот же маршрут нужен многим проектам — иначе шаблон придётся копировать на каждый.

**Когда не нужно.** Согласующий один и тот же для всех документов (гендиректор, юрист на весь
портал) — тогда группа пользователей или константа шаблона `Type: user` проще и прозрачнее.
Роль вычисляется из оргструктуры («руководитель автора») — для этого есть штатные механизмы
выбора сотрудника, карточка проекта не нужна.

## Как сделать

1. **Поля-роли в «Проектах».** В смарт-процессе проекта — пользовательские поля типа «Сотрудник»
   по одному на роль. Название поля и есть название роли в разговоре с заказчиком.
2. **Привязка документа к проекту.** В «Заявках» — поле типа «Привязка к элементам CRM»,
   настроенное на тип «Проекты». Когда в привязке разрешён один тип, значение поля — голый ID
   элемента; это и используется в фильтре ниже. Если типов разрешено несколько, значения приходят
   с префиксом типа — фильтр по `ID` тогда не годится, проверяйте на своём портале (мы этот случай
   не проверяли).
3. **Чтение роли в процессе.** Первым шагом — «Получить информацию об элементе CRM»: тип —
   «Проекты», фильтр `ID = {=Document:<поле-привязка>}`, в «возвращаемых полях» — коды полей-ролей.
   Дальше роль подставляется в исполнителей задания ссылкой на результат шага.

```yaml
# фрагмент спецификации tools/bpt; {{…}} — подстановка из снимка портала
- get_smart_item:
    id: project
    title: Роли из карточки проекта
    DynamicTypeId: "{{smart:Проекты}}"
    ReturnFields: ["{{field:Проекты/Бухгалтер проекта}}"]
    DynamicFilterFields:
      items: [[{object: Document, field: ID, operator: "=", value: "{=Document:{{field:Проект}}}"}, AND]]
- approve:
    id: accountant
    Users: ["{=@project:{{field:Проекты/Бухгалтер проекта}}}"]
    ApproveType: any
    Name: "Согласуйте заявку «{=Document:TITLE}»"
```

**Типы результатов обязательны.** Действие берёт типы возвращаемых значений из своего свойства
`DynamicEntityFields` (ядро, `setPropertiesTypes` в `crmgetdynamicinfoactivity.php`; в паспорте
действия — `ADDITIONAL_RESULT => ['DynamicEntityFields']`). В дизайнере оно заполняется само, при
сборке шаблона кодом его надо заполнять самому — иначе тип значения неизвестен и подстановка
сотрудника в исполнителей ненадёжна. `tools/bpt` заполняет это свойство по снимку портала
(см. раздел «Поля связанных смарт-процессов» в [SPEC.md](../../../tools/bpt/SPEC.md)); во всех
семи случаях корпуса клиента свойство тоже заполнено.

## Чего избегать

- **Пустая привязка роняет процесс.** Если у документа не заполнен проект (или у проекта — поле
  роли), действие завершается ошибкой «не найдено ни одного элемента», и процесс останавливается
  на первом шаге. Решайте явно: обязательное поле привязки в карточке, ветка-проверка перед
  чтением или осознанный отказ (тогда это вопрос заказчику, а не умолчание).
- **Роль в константе шаблона** вместо карточки: смена сотрудника — правка шаблона на каждом
  портале, а в выгрузке появляются зашитые ID — см. [[antipattern-bizproc-hardcoded-portal-ids]].
- **Чтение роли в каждой ветке.** Достаточно одного шага в начале: результат доступен дальше по
  всему процессу, в том числе во вложенных ветках и параллельных блоках.
- **Смена стадии до чтения роли.** «Сменить стадию» завершает процесс — шаги после неё не
  выполнятся (см. [[concept-bizproc-activity-catalog]]).

## Чем подтверждено

- Приём взят из практики команды и встречается в семи шаблонах клиента (корпус выгрузок из
  дизайнера БП).
- На стенде (коробка, `bizproc` 26.1075.0, `crm` 26.800.0) пять процессов с этим приёмом прогнаны
  сценариями целиком: заявка привязывается к «Проекту Альфа», задание приходит тому сотруднику,
  который указан в карточке проекта, процесс доходит до нужной стадии.
- В [оценке навыка «БП по ТЗ»](pattern-bizproc-ai-assisted-generation.md) агенты приходили к этому
  решению сами — по ТЗ вида «бухгалтер проекта» четыре решения из семи читали роль из карточки,
  без подсказки в задании.
