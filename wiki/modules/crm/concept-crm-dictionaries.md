# Справочники CRM

**TL;DR:** все перечисления CRM — источники, типы компаний, стадии лидов и сделок — лежат в одной
таблице `b_crm_status`. Значения читать через `CCrmStatus::GetStatus*` (с кэшем), связи и сложные
выборки — через `\Bitrix\Crm\StatusTable`, **писать только через `CCrmStatus`**. Источник —
[Справочники](https://bx24devbook.website.yandexcloud.net/Modul_CRM/Slovari/Spravocniki.html) «Книги
разработчика».

> **Сверено с книгой 2026-09-21.** Атрибуция исправлена (материал — из книги, не из apidocs).
> Уточнено: `StatusTable` — для связей и выборок, а не «для чтения» вообще; справочники — не
> исключение из D7, а частный случай общего правила «запись в таблицу — не действие»; убрано не
> подтверждённое книгой утверждение о своём справочнике модуля; добавлены практики про `STATUS_ID`.

## Что это и как работает

Справочник («статус», `crm_status`) — простое перечисление значений. Все справочники объединены в
таблице `b_crm_status` ключом `ENTITY_ID`.

| Поле | Смысл |
|---|---|
| `ENTITY_ID` | какой справочник (`SOURCE`, `STATUS`, `DEAL_STAGE`, …) |
| `STATUS_ID` | символьный код значения внутри справочника — **устойчивый**; числовой `ID` на разных порталах разный |
| `NAME` | отображаемое название (пользователь может менять) |
| `NAME_INIT` | исходное название — для «сбросить к системному» |
| `SORT` | порядок |
| `SYSTEM` | `Y`/`N` — можно ли удалить пользователю |
| `CATEGORY_ID` | направление (сделки; у лидов направлений нет) |
| `COLOR` | цвет |
| `SEMANTICS` | семантика статуса |

`CATEGORY_ID` / `COLOR` / `SEMANTICS` — надстройка ради стадий лидов и сделок: изначально таблица
проектировалась под плоские перечисления.

## Парадокс: новое API не для записи

| Задача | Класс | Почему |
|---|---|---|
| Значения справочника | `CCrmStatus::GetStatus*` | статический кэш |
| ORM-связи, сложные выборки | `\Bitrix\Crm\StatusTable` | стандартный путь D7 |
| Любое изменение | `\CCrmStatus` (старый API) | он **кэширует**; запись мимо него оставляет систему с устаревшим кэшем |

Книга формулирует это жёстко: изменять справочники через `StatusTable` противопоказано — часть
системных статусов кэшируется, и последствия могут быть необратимыми
([API для работы со статусами](https://bx24devbook.website.yandexcloud.net/Modul_CRM/Slovari/Spravocniki.html#api-dla-raboty-so-statusami)).

Это не столько исключение из правила «D7 — современный путь», сколько частный случай общего:
запись в таблицу — ещё не действие. Сущности CRM тоже пишут операциями фабрики или `CCrm*`, а
`*Table` используют для чтения; у справочников просто нет D7-обёртки для записи — см.
[[concept-bitrix-naming-conventions]].

## `CCrmStatus` — что нужно знать

**Чтение** (статические методы, с кэшем): `GetStatus($entityId)` — полные структуры;
`GetStatusList($entityId)` — `STATUS_ID => NAME`; `GetStatusListEx()` — то же с экранированием;
`GetFirstStatusID($entityId)`; `GetEntityTypes()` — все зарегистрированные справочники.

**Изменение** (на экземпляре с нужным `ENTITY_ID`): `Add`, `Update`, `Delete`; массово —
`BulkCreate($entityId, $items)`, `Erase($entityId)`.

Тонкости, на которых спотыкаются:

- `Update` меняет только `SORT`, `NAME`, `SYSTEM`, `COLOR`, `SEMANTICS`. Для `STATUS_ID` и
  `NAME_INIT` нужны опции `ENABLE_STATUS_ID` / `ENABLE_NAME_INIT`.
- `Delete($id)` работает **по первичному ключу**, не по `STATUS_ID`. Удаление несуществующего
  может дать фатальную ошибку.
- `Delete` **не проверяет**, что `ID` принадлежит указанному `ENTITY_ID` — имя справочника нужно
  только для очистки кэша. Ошибка в коде тихо удалит чужое значение.
- `Add($fields, $bCheckStatusId = true)` — флаг включает проверку дублей; `BulkCreate` ошибок **не
  сообщает** — после массовой вставки проверяйте результат выборкой.

## Семантика воронки живёт в метаданных

```php
'STATUS' => [
    'SEMANTIC_INFO' => [
        'START_FIELD'           => 'NEW',
        'FINAL_SUCCESS_FIELD'   => 'CONVERTED',
        'FINAL_UNSUCCESS_FIELD' => 'JUNK',
        'FINAL_SORT'            => 0,
    ],
]
```

Старт, успех и провал отдаёт `GetEntityTypes()` в `SEMANTIC_INFO` справочника, а у значений есть
колонка `SEMANTICS`. Может ли модуль зарегистрировать свой справочник с семантикой воронки, книга
не говорит — не опираться без проверки по коду.

## Почему важно при внедрении

Проектирование воронки ([[pattern-crm-sales-funnel-design]]) — это, по сути, наполнение
справочника стадий. Отсюда же цена [[antipattern-crm-stage-explosion|взрыва стадий]]: каждая
стадия — строка в общей таблице, которую видят отчёты, фильтры и автоматизация.

Методы фабрики Universal API по стадиям (`getStagesEntityId`, `getStages`, `getStage`,
`getStageSemantics`) — обёртки над этими же справочниками: UA не отменяет `b_crm_status`, а
инкапсулирует его.

## Практики
- **В интеграциях и миграциях ссылаться на `STATUS_ID`, а не на числовой `ID`** — сущности хранят
  код, а `ID` на разных порталах разный
  ([общая логика работы с полями](https://bx24devbook.website.yandexcloud.net/Modul_CRM/Slovari/Spravocniki.html#obsaa-logika-raboty-s-polami)).
- Шаг `SORT` — 10, начиная с 10: остаётся место вставить значение между.
- В своих справочниках `NAME_INIT` можно не заполнять — откатывать к системному нечего.

## Открытые вопросы
- Полный список системных `ENTITY_ID`.
- Полный набор значений `SEMANTICS`.
- Где именно живёт кэш `CCrmStatus::GetStatus` и как его гарантированно сбросить, если запись
  всё-таки прошла через ORM (книга: у `GetStatus` статический кэш, `ENTITY_ID` в `Delete` нужен для
  его сброса).
