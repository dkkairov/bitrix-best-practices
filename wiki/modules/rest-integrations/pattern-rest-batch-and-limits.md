# Батчи и лимиты REST

## Проблема и контекст

Интеграция, написанная «в лоб» — по одному HTTP-запросу на объект, — упирается в ограничения
портала: сначала растёт время синхронизации, потом приходят `QUERY_LIMIT_EXCEEDED` и
`OPERATION_TIME_LIMIT`, а в худшем случае REST блокируется целиком (`OVERLOAD_LIMIT`). Переписывать
интеграцию под это постфактум дорого, поэтому решение принимается на старте.

## Решение

Собирать запросы в **`batch`**: один вызов вместо нескольких, с возможностью передать результат
одного подзапроса в следующий.

```bash
curl -X POST -H "Content-Type: application/json" -d '{
    "halt": 0,
    "cmd": {
        "get_user":        "user.current",
        "get_department":  "department.get?ID=$result[get_user][UF_DEPARTMENT][0]"
    }
}' https://<портал>/rest/<id>/<код-вебхука>/batch
```

| Параметр | Назначение |
|---|---|
| `cmd` | массив подзапросов: ключ — идентификатор, значение — `метод?параметр=значение` |
| `halt` | прерывать ли цепочку при ошибке; по умолчанию `false` |
| `method` / `query` / `as` | форма REST 3.0: имя метода, его параметры и имя результата |

**Связывание подзапросов** — через `$result[<ключ>][<поле>]`. Это и есть главная выгода: выборка и
зависимые операции уезжают одним обращением, без промежуточных round-trip.

В SDK то же самое: `BX24.callBatch({...})` в JS, `CRest::callBatch([...], $halt)` в PHP.

## Разбор ответа

Ответ батча — не просто массив результатов:

| Ключ | Что внутри |
|---|---|
| `result` | результаты успешных подзапросов, по их ключам |
| `result_error` | ошибки подзапросов — **по одному на подзапрос** |
| `result_total` | общее количество записей для методов со списками |
| `result_next` | смещение для следующей страницы |
| `result_time` | время каждого подзапроса |

**При `halt = 0` частичный отказ выглядит как успех:** HTTP-ответ 200, а `result` пуст и всё лежит в
`result_error`. Код, который проверяет только код ответа, молча потеряет данные. Проверять надо
`result_error` по каждому ключу.

## Когда применять
- Массовые операции: импорт, синхронизация, регулярная выгрузка.
- Цепочки «получить — использовать»: выборка, затем зависимые вызовы по её результату.
- Любая интеграция, которая будет работать по расписанию, а не разово.

## Когда НЕ применять
- Единичный вызов в ответ на действие пользователя — батч только добавит сложности.
- Методы, которые в батче запрещены: ответ `ERROR_BATCH_METHOD_NOT_ALLOWED`. Такие вызовы остаются
  одиночными.

## Ошибки, к которым нужно быть готовым

| Код | Смысл | Что делать |
|---|---|---|
| `ERROR_BATCH_LENGTH_EXCEEDED` | превышена длина пакета | разбить на пакеты меньшего размера |
| `ERROR_BATCH_METHOD_NOT_ALLOWED` | метод нельзя вызывать в батче | вынести из пакета |
| `QUERY_LIMIT_EXCEEDED` | слишком много запросов | пауза и повтор с выдержкой |
| `OPERATION_TIME_LIMIT` | метод заблокирован по времени операций | снизить темп, разнести по времени |
| `OVERLOAD_LIMIT` | REST заблокирован из-за перегрузки | остановиться, разбираться с нагрузкой |
| `expired_token` | истёк токен | обновить ([[recipe-rest-oauth-app-setup]]) |
| `insufficient_scope` | у вебхука/приложения нет нужного права | добавить scope |
| `PORTAL_DELETED` | портал удалён | прекратить попытки, а не ретраить |

Обработка перечисленных кодов — тема [[pattern-rest-reliable-delivery]].

## Последствия
- **Плюсы:** меньше обращений, быстрее синхронизация, ниже риск упереться в лимиты.
- **Минусы:** ошибки приходят «россыпью» по подзапросам, и их надо разбирать; отладка сложнее,
  чем у одиночного вызова; `halt = 0` требует дисциплины при проверке ответа.
