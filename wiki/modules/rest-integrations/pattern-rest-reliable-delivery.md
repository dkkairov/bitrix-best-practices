# Надёжная доставка событий

## Проблема и контекст

Исходящий вебхук — доставка «выстрелил и забыл». Если принимающая сторона в этот момент лежала,
перезагружалась или ответила таймаутом, событие потеряно, и узнают об этом через неделю по
расхождению данных. Для обмена с учётной системой, где каждый документ важен, этого мало.

Вторая беда — обратная: сеть моргнула, отправитель повторил, и в базе появился дубль.

## Решение

Три механизма вместе. Первый — штатный, два других на вашей стороне.

### 1. Офлайн-события — очередь на стороне портала

Вместо «портал стучится к нам» — «мы забираем из очереди». Портал копит события, приложение
вычитывает их, когда готово.

| Метод | Что делает |
|---|---|
| `event.offline.get` | возвращает первые события очереди **и снимает их** |
| `event.offline.list` | читает очередь **без изменения состояния** — для диагностики |

```php
CRest::call('event.offline.get', [
    'filter' => ['=EVENT_NAME' => 'ONCRMLEADADD', '>=ID' => 1],
    'auth_connector' => 'my-connector',
]);
```

Фильтр поддерживает `ID`, `TIMESTAMP_X`, `EVENT_NAME`, `MESSAGE_ID` с операциями `=`, `>`, `<`,
`>=`, `<=`, `!=`. Метод требует прав **администратора**.

Событие в ответе: `ID`, `TIMESTAMP_X`, `EVENT_NAME`, `EVENT_DATA`, `EVENT_ADDITIONAL`, `MESSAGE_ID`.

**Ключевое отличие от исходящего вебхука:** падение вашего сервиса не теряет события — они лежат в
очереди до следующего вычитывания.

### 2. Повторы с разбором кода ошибки

Не все ошибки одинаковы: часть означает «подожди и повтори», часть — «повторять бессмысленно».

| Код | Повторять? |
|---|---|
| `QUERY_LIMIT_EXCEEDED`, `OPERATION_TIME_LIMIT`, `OVERLOAD_LIMIT` | да, с возрастающей паузой |
| `INTERNAL_SERVER_ERROR`, `ERROR_UNEXPECTED_ANSWER` | да, ограниченное число раз |
| `expired_token` | обновить токен и повторить один раз |
| `insufficient_scope`, `ACCESS_DENIED`, `INVALID_CREDENTIALS` | **нет** — чинить конфигурацию |
| `ERROR_METHOD_NOT_FOUND`, `INVALID_REQUEST` | **нет** — чинить код |
| `PORTAL_DELETED` | **нет** — остановить интеграцию совсем |

Повтор без разбора кода превращает ошибку конфигурации в бесконечный цикл, который и приводит к
`OVERLOAD_LIMIT`.

### 3. Идемпотентность на приёмной стороне

У события есть `ID` и `MESSAGE_ID` — храните обработанные и отбрасывайте повторы. Для операций
записи в Bitrix24 держите на своей стороне соответствие «внешний ключ → ID объекта в портале»:
перед созданием проверяйте, не создан ли объект раньше.

Без этого любой повтор рождает дубль, а дубли в CRM — самая дорогая в разборе проблема внедрения.

## Когда применять
- Обмен с учётной системой, где потеря документа недопустима.
- Интеграция, которая должна пережить плановые перезагрузки приёмной стороны.
- Любой сценарий с записью в Bitrix24 из внешней системы.

## Когда НЕ применять
- Уведомления, где потеря одного события несущественна (оповещение в чат) — там дешевле исходящий
  вебхук.
- Разовая миграция: она делается под присмотром, очередь избыточна.

## Последствия
- **Плюсы:** события переживают недоступность приёмника; повторы не плодят дубли; ошибки
  конфигурации видны сразу, а не маскируются бесконечными ретраями.
- **Минусы:** нужен планировщик на своей стороне и хранилище обработанных идентификаторов;
  `event.offline.get` требует прав администратора; события приходят с задержкой до следующего
  вычитывания.

## Подводные камни
- **`event.offline.get` снимает события с очереди.** Если обработка упала после получения, но до
  сохранения — события потеряны. Сначала сохраняем сырьё, потом обрабатываем.
- Для диагностики смотреть очередь только через `event.offline.list` — `get` изменит состояние.
- Массовое вычитывание сочетать с [[pattern-rest-batch-and-limits|батчами]]: обработка сотен
  событий по одному вызову на событие сама упрётся в лимиты.
