## TL;DR
Universal API — современный единообразный способ работы с CRM-сущностями: `Container` → `Factory`
→ `Item` + `Operation`. Расширяется действиями операций, а не обработчиками событий. Рядом —
словарный слой (`b_crm_status`, мультиполя), который UA инкапсулирует, но не отменяет.

## Ключевые тезисы
- UA создан ради трёх целей: убрать дублирование кода, снизить связность, сделать CRM тестируемой.
  Плата — выросшая сложность изучения.
- Канонический сценарий всегда один: фабрика из контейнера → элемент → правка → операция → запуск.
- UA включён всегда для смарт-процессов, счетов, предложений и документов; для лида, сделки,
  контакта и компании — опционально, и переключить настройку может любой пользователь с доступом
  в CRM.
- Операция — это порядка 15 шагов; вмешиваться следует действиями (`ACTION_BEFORE_SAVE` /
  `ACTION_AFTER_SAVE`), а не событиями.
- Главный довод против событий назван в самом источнике: в обработчик приходят **только изменённые
  поля**, плюс общее статическое состояние между `before` и `after` даёт ошибки при работе с двумя
  объектами подряд.
- Все справочники CRM лежат в одной таблице `b_crm_status`; читать следует через `StatusTable`,
  а **изменять — только через `CCrmStatus`**, потому что он кэширует. Это прямое исключение из
  правила «D7 — современный путь».
- Семантика воронки (старт, успех, провал) хранится метаданными справочника, а не в коде.
- Мультиполя всех сущностей — в одной таблице `b_crm_field_multi`, с пакетной записью через
  `SetFields`, где пустое значение означает удаление.
